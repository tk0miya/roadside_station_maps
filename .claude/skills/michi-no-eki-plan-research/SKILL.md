# 道の駅 整備計画データの調査・更新

人手で管理している開発計画スプレッドシートの `status` / `date` / `name` / `memo` を Web 調査で最新化する。

このデータは人が育ててきた台帳で、誤った上書きは人が手で戻すことになる。**調査と更新は必ず分ける** — 調べた結果はいったん報告し、ユーザーの承認を得てから書き込む。承認なしに `plan:update` を実行しない。

## 全体の流れ

1. 対象を取り出す
2. サブエージェントに分けて並列で調べる
3. 結果を集約して報告し、承認を得る
4. 承認された項目だけ更新する

駅 1 件をどう調べ、何を書くかをどう決めるかは `references/research.md` にある。サブエージェントに読ませるほか、1〜2 件だけを自分で調べるときと、集約した結果を検算するときにも使う。

## 1. 対象を取り出す

```bash
npm run --silent plan:list | jq '[.[] | select(.status == "登録済み" or .status == "計画中")]'
```

`開業` と `中止` は対象外（終わった話なので動かない）。調べる駅を名指しされていなければ、残った全件を調べる。

一覧を眺めるだけなら `| jq -r '.[] | [.status, .pref, .city, .name, .date] | @tsv'` を足す。サブエージェントに配るのは JSON のまま。

## 2. サブエージェントに分けて並列で調べる

1 件あたり検索 1〜3 回とページ取得が要るので、全件を 1 つのコンテキストで回すと溢れる。調査は駅ごとに独立していて共有状態がないため、**10 件ずつサブエージェントに割り当てて並列で走らせる**。

各サブエージェントに渡すもの:

- `references/research.md` を**最初に読ませる指示**（絶対パスで渡す）
- 担当する駅の行。`plan:list` の JSON から該当分をそのまま抜き出して渡す。**`memo` を落とさない** — 既存 URL が生きているかの確認に要る

守らせること:

- **書き込みは一切させない。** `plan:list` の読み取りと Web 調査だけ。`plan:update` は禁止
- **戻り値は構造化データに固定する。** 新しい情報があった駅は `{name, pref, 提案する変更（date / status / name）, 追加する URL, 根拠, 気づいたデータの不備}`、なかった駅は名前だけの一覧（ただし不備に気づいた駅はそれを添える）。自然文で返させると集約が破綻する

全件を並列で回すと本体は一次情報に触れないので、`pref` / `city` の誤りやリンク切れは**サブエージェントが返さなければ報告に上がらない**。戻り値からこの欄を落とさない。

全バッチを一度に投げてよい。同時実行数はハーネス側が抑えるので、こちらで区切る必要はない。

集約時は、`date` の粒度が担当ごとにぶれていないかを `references/research.md` の変換表と突き合わせて検算する。

## 3. 報告

更新の前に必ず報告する。この形式で書く:

```markdown
◯◯ 件を調査し、うち ◯◯ 件に新しい情報があった。

## 更新すべきレコード
### 駅名（pref city / status / date: 現在値）
何が分かったか（1〜2 行）
- `date`: 現在値 → **新値**
- `name`: 現在値 → **新値**（正式名称・愛称が判明したとき）
- `memo` 追加: [出典タイトル](URL)

## memo だけ追加したいもの
（表で駅名・新情報・URL）

## データの不備
（`pref` / `city` の誤り、リンク切れなど）
```

**新しい情報がなかった駅は報告に載せない。** 扱う件数が多いので、列挙すると要点が埋もれる。調べた範囲は冒頭の件数で伝わる。ただし `pref` / `city` の誤りやリンク切れに気づいた駅は、更新の材料がなくても「データの不備」に載せる。

**`pref` / `city` は CLI から更新できない**（意図的な除外で、理由は `src/scripts/plan.ts` の `UPDATABLE_FIELDS` のコメントにある）。誤りを見つけたら報告に載せるだけにして、修正はユーザーがスプレッドシート上で行う。

## 4. 更新

承認された項目だけを実行する。**`plan:update` に dry-run はない。** 動作を確かめるつもりで叩いても実データが書き換わるので、挙動の確認は `plan:list` 側だけで行う。

**通信エラーが返っても書き込みが済んでいることがある。** GAS は書き込んでから応答するので、`fetch failed` はそれ以前に失敗したことを意味しない。これを見たら「反映されなかった」と決めつけず、`plan:list` で現在値を確かめてから報告する（引数の検証エラーは送信前に落ちるので、こちらは確認不要）。

エントリは**駅名と都道府県の 2 つの位置引数**で特定する。どちらも `plan:list` の値をそのままコピーする。

```bash
npm run plan:update -- "道の駅 石川町" 福島県 --date=2026-09-18
npm run plan:update -- "道の駅 共和町" 北海道 --status=登録済み
npm run plan:update -- "道の駅 あつみ (移転)" 山形県 --name="道の駅 うぇるかぶ (移転)"
```

**駅名はクォートする。** ほぼすべて空白を含むので、実質どの呼び出しでも要る。忘れるとシェルが空白で分割するが、CLI が止める。都道府県の形（`都` / `道` / `府` / `県` で終わるか）が崩れていれば `Invalid prefecture: ...`、崩れずに引数が余れば `Unexpected extra arguments. Quote the name: ...` になる。黙って別のエントリを引くことはない。

### memo の追記

**`--memo` は上書きなので、そのまま渡すと既存の URL が全部消える。** 追記するには現在値を読んで改行で連結する:

```bash
MEMO=$(npm run --silent plan:list |
  jq -r '.[] | select(.name == "道の駅 川崎町" and .pref == "福岡県") | .memo')
npm run plan:update -- "道の駅 川崎町" 福岡県 --memo="$MEMO
https://example.com/news"
```

**この 2 行は 1 回のコマンド実行でまとめて走らせる。** 別々に実行するとシェルが変わって `$MEMO` が空になり、CLI は値を trim するので「新しい URL 1 本だけ」が正常な更新として書き込まれる。既存の出典が消えたまま `Updated ...` が返るので、エラーでは気づけない。書き込んだら `plan:list` で memo を読み直して、既存の URL が残っているか確かめる。

`$MEMO` と URL の間で改行すると、それが値の中の区切りになる。URL を複数足すなら行を重ねる。同じ URL が `$MEMO` に既にあれば足さない — 同じ駅を後日また調べると重複しやすい。

**`jq` の絞り込みも `name` と `pref` の両方で行う。** `name` だけで引くと同名エントリの memo が 2 件分連結されて `$MEMO` に入り、それを書き戻すと片方の出典がもう片方に流れ込む。書き込み先を正しく指定していても防げない。

同じ駅の `name` と `memo` を両方更新するときは、**memo の追記を先に済ませてから改名する。** 先に改名すると、旧名で引いた `$MEMO` が空になる。

## 前提

`PLAN_API_URL` が `.env` に必要（`.env.example` 参照）。`plan:list` がエラーになるときはまずこれを確認する。

`npm run --silent` の `--silent` は必須 — 付けないと npm のバナーが stdout に出て `jq` が壊れる。
