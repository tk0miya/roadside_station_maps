# 道の駅 整備計画データの調査・更新

人手で管理している開発計画スプレッドシートの `status` / `date` / `name` / `memo` を Web 調査で最新化する。

このデータは人が育ててきた台帳で、誤った上書きは人が手で戻すことになる。**調査と更新は必ず分ける** — 調べた結果はいったん報告し、ユーザーの承認を得てから書き込む。承認なしに `plan:update` を実行しない。

## 全体の流れ

1. `checked_on` の古い順に 10 件取り出す（§1）
2. 1 駅ずつ、Web で調べてその駅の書く値を決めるところまでを片付ける（§2・§3）
3. 10 件をまとめて報告し、承認を得る（§4）
4. 調査した全件に `plan:update` を実行してセッションを終える（§5）

§3 は列ごとの決め方をまとめた節で、調査の後段ではなく**調査しながら引く**。`date` の裏取り（延期の確認）のように追加の検索が必要になる判断もそこに書いてある。

## 1. 対象を取り出す

`checked_on`（最後に調査した日）が古い順に 10 件だけ取る。

```bash
npm run --silent plan:list \
  | jq '[.[] | select(.status == "登録済み" or .status == "計画中")] | sort_by(.checked_on) | .[:10]'
```

`開業` と `中止` は対象外（終わった話なので動かない）。

**1 セッションで扱うのはこの 10 件だけ。** WebSearch の回数上限は**ターンではなく Claude Code のセッション単位**なので、対象を全件調べようとすると途中で使い切って、どこまで終わったのか分からない状態で止まる。少しずつ調べて `checked_on` を進め、**セッションを分けて繰り返し一周させる**設計にしている。1 回で終わらせようとしない。

**調査は 1 セッションに 1 回だけ。** 10 件を終えたら 2 バッチ目を始めない（依頼されても同じ）。上限がセッション単位なので 2 回目は 1 回目の残りで走ることになり、その残量を知る手段がない。収まるか判断できないまま始めて途中で枯渇すると、その回の調査が無駄になる。**続きは新しいセッションで行う**（セッションを分け直すコストはほぼゼロで、賭けに負けたときのコストだけが大きい）。

調べる駅を名指しされたときは、古い順ではなくその駅を調べる。**1 セッション 10 件の上限は同じ** — 検索の上限は誰が対象を選んだかに関係なく効く。超える分は次のセッションに回し、残した駅を報告に列挙する（名指しの駅はキューの順番に乗らないので、書き残さないと次に何を調べるべきか分からなくなる）。

未調査の駅（`checked_on` が空）は空文字が先頭に並ぶので、自動的に最優先になる。人がシートに追加した新しい行がまずここに入る。

一覧を眺めるだけなら `| jq -r '.[] | [.checked_on, .status, .pref, .city, .name, .date] | @tsv'` を足す。

## 2. 駅ごとに調べる

**1 駅ずつ閉じてから次へ移る。** 調べ終えた駅ごとに、**提案する変更（`date` / `status` / `name`）・足す出典リンク（`[タイトル](URL)`）・気づいたデータの不備**を短く書き留める（§3 が列ごとの決め方）。報告とそのあとの `plan:update` の材料になり、検索結果とページ本文を 10 件分抱えたまま進まずに済む — 報告の前にコンテキストが尽きると、そこまでに使った検索がまるごと無駄になる。**新しい情報がなかった駅も「調べた」ことは残す** — §5 の `plan:update` は調べた駅すべてが対象で、取りこぼすとその駅は調査済みにならず次のセッションでまた引かれる。

### 検索クエリの組み立て

**`city` から郡名を除去する。** 郡名を含めると検索がヒットしない。

- `上伊那郡箕輪町` → `箕輪町`
- `高岡郡佐川町` → `佐川町`
- `さいたま市岩槻区` → そのまま（政令市の区は地名として機能する）

**`pref` を必ず含める。** 市町村名だけだと同名地名を拾う（「白石市」の検索で札幌市白石区が上位に来る）。

**`name` が仮称でなければ `name` で検索する。** 「道の駅 ◯◯市」「道の駅 ◯◯町」の形は仮称なので `city` で検索する。「みのわテラス」「くるん熊谷」のような固有名は、それ自体で検索した方がはるかに精度が高い。

```
道の駅 {pref} {city} 開業        ← 仮称の場合
{name} 開業 いつ                  ← 固有名がある場合
```

### 既存の道の駅と取り違えない

1 つの市区町村に道の駅が複数あることは珍しくない（南房総市には 8 駅、高山市にも 8 駅ある）。検索すると、その市区町村に既にある駅の記事が上位に来る。

調べているのは**新設・再整備の計画**なので、既存駅の話だと分かれば読み飛ばす。対象の市区町村にどんな駅があるかを、調査を始める前に引いておく:

```bash
grep "南房総市" data/stations.csv | cut -f3   # リポジトリルートで実行する
```

`data/stations.csv` は michi-no-eki.jp のスクレイピング結果（拡張子に反して TSV）で、既存駅を引く用途に使う。**ただし登録済みかどうかの判定には使えない。** 登録されても掲載が遅れることがあるので、載っていないことは未登録の根拠にならない。

地名が似た別の駅が紛れ込むこともある（南アルプス市を調べると、長野県伊那市の「南アルプスむら長谷」が出てくる）。判断に迷ったら所在地と開業時期を見る。既に開業している駅の記事なら、調査対象ではない。

### 記事の日付は自分で確かめる

検索結果は新しい順には並ばず、数年前の記事が最上位に来る。**WebSearch は `after:` などの検索演算子を解釈しないので、クエリ側で期間を絞ることはできない。**

**開いて日付を確認してから判断の材料にする。** 古い記事しか出てこなければ「進捗なし」の根拠になる。日付が書かれていないページ（まとめサイトに多い）はいつの情報か分からないので、根拠にしない。

### 出典の優先順位

1. **自治体の公式サイト** — 一次情報。ただし更新が遅く、決定済みの情報が載っていないこともある
2. **地方紙・地方建設業紙** — 開業日の速報はここが早い。優先交渉権者の決定なども載る
3. **国交省・地方整備局** — 登録の確定情報
4. まとめサイト・個人ブログ — 古い情報が残りがちなので、他に裏が取れないときの補助に留める

### 自治体ページの中身は PDF のことが多い

一覧ページを開いても概要しか書いておらず、日程は添付 PDF にある、というパターンが頻出する。ページを WebFetch して「添付 PDF へのリンクを URL ごと列挙して」と指示すればリンクを拾える。

Bash のサンドボックスは許可ホストにしかネットワークを通さないので、`curl -s "<url>" | grep -oE 'href="[^"]*\.pdf"'` が通るとは限らない。試すのは自由だが、弾かれたら WebFetch に切り替える。

拾った PDF を WebFetch にかける。ただし**画像 PDF はこの環境ではテキスト化できない**（`pdftoppm` が入っていない）。読めなければ深追いせず、同じ内容を報じた記事を探す方が早い。

## 3. 書く値を決める

### date

シートは**判明している粒度をそのまま記録する**列で、`2026-09-18` も `2026` も `2026夏` も等しく正しい値。**変換してよいのは和暦 → 西暦だけで、それ以外は出典の言葉をそのまま写す。**

| 出典の表現 | 書く値 | |
|---|---|---|
| 令和 9 年 7 月オープン | `2027-07` | 月まで言い切っているので日付形式にできる |
| 令和 9 年度初頭 | `2027年度初頭` | ✗ `2027-04` — 「初頭」が何月かは出典が言っていない |
| 令和 9 年夏ごろ | `2027夏ごろ` | ✗ `2027-07` |
| 2028 年度 | `2028年度` | ✗ `2028` — 年度は 2029 年 3 月まで含む |
| 2026 年度下半期 | `2026年度下半期` | ✗ `2026` — 暦年をまたぐ |

「初頭」「上半期」「ごろ」を月に置き換えるのは、出典にない情報を足す行為で、**後から見たときに確定情報と区別がつかなくなる**。これがこの列でいちばん避けたい壊れ方なので、粒度を上げる方向にも下げる方向にも丸めない。

日本語混じりの表記で地図が壊れるものはない。`計画中(予定あり)` / `計画中(未定)` の振り分けは `date` の有無だけで決まり（`src/frontend/types/plan.ts`）、値そのものは解釈できなくても支障がない。

年度と暦年の区別だけは意識しておく — 「令和 9 年度」は 2027 年 4 月〜2028 年 3 月であって 2027 年ではない。ただし気づいたからといって暦年に直すのではなく、年度のまま書く。

#### 開業が近いものは「延期」を疑う

`date` が 1〜2 年以内のレコードでは、**開業日が前倒しで確定するより延期される方が多い**。自治体は延期を「開業時期の延期について」のような専用ページで公表するので、既存の `date` を裏付ける情報だけで満足せず、より新しい発表がないか確認する。

延期の告知には「最終的な時期は◯月ごろ公表予定」と続きが予告されていることがある。見つけたら報告に含める — いつ再調査すべきかの判断材料になる。

### status

`計画中` / `登録済み` / `開業` / `中止` の 4 値のみ。

**登録は必ずニュースになる。** 国交省の登録は年 2 回（6 月・12 月）にまとまって公示され、登録証の交付は自治体の発表や地方紙の記事になる。自治体が「登録を目指す」と書いているだけでは `計画中` のまま。

`開業` への変更は、開業日が過ぎて実際に開いたことが確認できたときだけ。予定日を過ぎただけでは変えない（延期はよくある）。

### name

正式名称や愛称が判明したら変更を提案する（「道の駅 石川町」に対して正式名称が「道の駅石川」、仮称だった駅に「うぇるかぶ」のような愛称が決まった、など）。

**表記は出典の正式名称をそのまま写す。** `date` と同じ考え方で、シートの体裁に合わせて空白を足したり削ったりしない。ただし `(移転)` `(再整備)` はシート独自の区別で正式名称の一部ではないので、改名しても残す。

### memo

出典を改行区切りで並べた列。基準は「後から根拠を辿れるか」で、同じことを言っている記事を何本も足す必要はない。

**リンクは `[タイトル](URL)` 形式で書く。** 地図の情報ウィンドウ（`src/frontend/plan-memo.ts`）はこの記法をタイトル付きのハイパーリンクとして描画する（裸の URL もリンクにはなるが、幅の狭いウィンドウに URL がそのまま並ぶと何のページか分からない）。タイトルは出典ページの見出しをそのまま写す（`[速報]` のような半角角括弧は `［速報］` に直す — タイトルに `]` が入るとリンクとして解釈されず、角括弧を含む地の文と URL ラベルの裸リンクに分かれてしまう）。**既存の裸 URL は書き換えない** — タイトルを付けるにはページを開き直すことになり、§1 で節約している検索・取得の予算をそこに使う理由がない。

## 4. 報告

更新の前に必ず報告する。この形式で書く:

```markdown
◯◯ 件を調査し、うち ◯◯ 件に新しい情報があった。

## 更新すべきレコード
### 駅名（pref city / status / date: 現在値）
何が分かったか（1〜2 行）
- `date`: 現在値 → **新値**
- `name`: 現在値 → **新値**（正式名称・愛称が判明したとき）
- `memo` 追加: [出典タイトル](URL)

## memo だけ追加したいもの
（表で駅名・新情報・出典リンク `[タイトル](URL)`）

## データの不備
（`pref` / `city` の誤り、リンク切れなど）
```

**新しい情報がなかった駅は報告に載せない。** 扱う件数が多いので、列挙すると要点が埋もれる。調べた範囲は冒頭の件数で伝わる。

「データの不備」に書くのは、調査のついでに気づいた `pref` / `city` の誤り（所在地が実際と違う）や、既存 `memo` の URL が 404 になっていることなど。これらは調べた本人にしか見えないので、報告に上げないと誰も気づかない。更新の材料が出てこなかった駅でも、不備に気づいたならここに載せる。

ここに載せた内容は、承認後に `--report` で Slack にも流す（§5）。承認のやり取りで生まれたこと（却下された提案など）も同じ経路で流す。

**`pref` / `city` は CLI から更新できない**（意図的な除外で、理由は `src/scripts/plan.ts` の `UPDATABLE_FIELDS` のコメントにある）。誤りを見つけたら報告に載せるだけにして、修正はユーザーがスプレッドシート上で行う。

キューの残りはここでは報告しない。更新を終えてから数える（§5 の最後）。

## 5. 更新

書き込むのは承認された項目だけ。**`plan:update` に dry-run はない。** 動作を確かめるつもりで叩いても実データが書き換わるので、挙動の確認は読み取り側（`plan:list` / `plan:show`）だけで行う。

**通信エラーが返っても書き込みが済んでいることがある。** GAS は書き込んでから応答するので、`fetch failed` はそれ以前に失敗したことを意味しない。これを見たら「反映されなかった」と決めつけず、`plan:show` で現在値を確かめてから報告する（引数の検証エラーは送信前に落ちるので、こちらは確認不要）。

エントリは**駅名と都道府県の 2 つの位置引数**で特定する。どちらも `plan:list` の値をそのままコピーする。

```bash
npm run plan:update -- "道の駅 石川町" 福島県 --date=2026-09-18
npm run plan:update -- "道の駅 共和町" 北海道 --status=登録済み
npm run plan:update -- "道の駅 あつみ (移転)" 山形県 --name="道の駅 うぇるかぶ (移転)"
```

**駅名はクォートする。** ほぼすべて空白を含むので、実質どの呼び出しでも要る。忘れるとシェルが空白で分割するが、CLI が止める。都道府県の形（`都` / `道` / `府` / `県` で終わるか）が崩れていれば `Invalid prefecture: ...`、崩れずに引数が余れば `Unexpected extra arguments. Quote the name: ...` になる。黙って別のエントリを引くことはない。

### 調査した全件に update を実行する

報告の承認を得たら、**調査した駅すべてについて `plan:update` を実行する。** `checked_on`（最後に調査した日）はこのコマンドが書く。承認は報告に対して 1 回もらうもので、報告に載せていない駅（新しい情報がなかった駅）と提案を却下された駅も対象に含める。書く値がなければキーだけを渡す:

```bash
npm run plan:update -- "道の駅 共和町" 北海道
```

**実行するのは実際に調べた駅だけ。** 10 件に届かないまま終えるなら、調べた分にだけ実行して残りは次のセッションに回す。調べていない駅に実行すると、調査済みとしてキューの最後尾に回る。

### シートに書けないことは `--report` で送る

`plan:update` の成功はスプレッドシートを見ている人には見えないので、更新内容は Slack に投稿される。ただし投稿されるのは**シートに書き込まれた値だけ**なので、書き込めない情報は `--report` に添える。これも同じ Slack 投稿に載る。

```bash
npm run plan:update -- "道の駅あ" 福井県 --report="city が誤り。実際は坂井市（出典: https://example.com/news）"
npm run plan:update -- "道の駅い" 福島県 --date=2026-09-18 --report="memo の 2 本目の URL が切れている"
```

`--report` に書くのは、調査と承認のやり取りから出たもののうちシートに残せないもの:

- `pref` / `city` の誤り（CLI から更新できない）
- リンク切れ
- 却下された提案（人が後から判断を見直せるようにする）
- 判断がつかず人に決めてほしいこと

書き方の約束:

- **1 駅 1 件。** その駅の `plan:update` に添える。上の 4 種類のうち複数該当するなら、落とさず 1 つの文にまとめる。どの駅にも紐づかない話（キューの残りなど）は送れないので、最終応答に書く
- **文単位で完結させる。** Slack にはこの 1 行しか届かず、会話の文脈は追えない。駅名は自動で付くので繰り返さない
- **空の `--report=` はエラーになる。** 報告することがなければオプション自体を付けない（更新も報告もない `plan:update` は Slack に何も投稿しない — 調査済みの記録としては `checked_on` が残る）
- **シートには残らない。** 人が対応しなければ消えるが、その駅は次の周回で再び調査対象になるので、同じ不備なら再度報告されればよい

### memo の追記

**`--memo` は上書きなので、そのまま渡すと既存の URL が全部消える。** 追記するには現在値を読んで改行で連結する。`plan:show` は `plan:update` と同じキーで 1 件を引くので、読む先と書く先がずれない:

```bash
MEMO=$(npm run --silent plan:show -- "道の駅 川崎町" 福岡県 | jq -r .memo)
npm run plan:update -- "道の駅 川崎町" 福岡県 --memo="$MEMO
[道の駅◯◯ 開業日が決定](https://example.com/news)"
```

**この 2 行は 1 回のコマンド実行でまとめて走らせる。** 別々に実行するとシェルが変わって `$MEMO` が空になり、CLI は値を trim するので「新しい URL 1 本だけ」が正常な更新として書き込まれる。既存の出典が消えたまま `Updated ...` が返るので、エラーでは気づけない。書き込んだら `plan:show` で読み直して、既存の URL が残っているか確かめる（Slack 投稿にも消えた行が `-` 付きで出るので、そこでも気づける）。

**追記するタイトルに `` ` `` `$` `"` が含まれるなら落としてから書く。** `--memo` は二重引用符の中に置くので、そのまま渡すとシェルが展開・分割し、見出しと違う文字列が黙って書き込まれる（バッククォートに至ってはコマンドとして実行される）。URL 側にこれらが入っている場合は落とさず `\` でエスケープする — 1 文字欠けるとリンクを辿れなくなる。

`$MEMO` と追記分の間で改行すると、それが値の中の区切りになる。出典を複数足すなら行を重ねる。同じ URL が `$MEMO` に既にあれば足さない — 同じ駅を後日また調べると重複しやすい。タイトルが違っても URL が同じなら同じ出典として扱う。

同じ駅の `name` と `memo` を両方更新するときは、**memo の追記を先に済ませてから改名する。** 先に改名すると、旧名で引いた `$MEMO` が空になる。

### 締めにキューの残りを報告する

書き込みが済んだら、シートを読み直して残りを伝える。1 回では一周しないので、次のセッションを走らせるべきかの判断材料になる。**update より前に数えてはいけない** — 今調べた 10 件が古いままの側に数えられる。

```bash
npm run --silent plan:list \
  | jq '[.[] | select(.status == "登録済み" or .status == "計画中")] | sort_by(.checked_on) as $entries
        | ($entries[0].checked_on) as $oldest
        | {total: ($entries | length),
           oldest: $oldest,
           at_oldest: ([$entries[] | select(.checked_on == $oldest)] | length)}'
```

> 対象は全 ◯◯ 件。いちばん古い `checked_on` は YYYY-MM-DD で ◯◯ 件。

`at_oldest` は最古のスタンプを共有する件数で、ここが 10 件ずつ削られていくことで一周が進む。`oldest` が空なら、まだ一度も調べていない行（人が追加したばかりの行）が残っているので「未調査が ◯◯ 件」と書く。

`oldest` がまだ古いなら「続きは新しいセッションで」を添える。全件が十分に新しければ足さない — 一周し終わった直後にもう一度走らせても、いちばん新しい駅を調べ直すだけになる。

## 前提

`PLAN_API_URL` が `.env` に必要（`.env.example` 参照）。`plan:list` がエラーになるときはまずこれを確認する。

`npm run --silent` の `--silent` は必須 — 付けないと npm のバナーが stdout に出て `jq` が壊れる。
