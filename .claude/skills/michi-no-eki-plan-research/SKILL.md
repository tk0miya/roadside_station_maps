# 道の駅 整備計画データの調査・更新

開発計画マスタ `data/plans.json` の `status` / `date` / `name` / `urls` を Web 調査で最新化する。

## 全体の流れ

1. 対象を取り出す — `checked_on` の古い順に 10 件
2. 駅ごとに調べて書く — 1 駅を調べ、値を決め、その場で `data/plans.json` に書いてから次へ移る
3. コミットして PR を出す

番号は以降の節に対応する。

## 1. 対象を取り出す

対象は `data/plans.json` から選ぶ。`checked_on`（最後に調査した日）が古い順に 10 件だけ取る。

```bash
npm run --silent plan -- list --status=登録済み,計画中,凍結 --sort=checked_on --limit=10
```

`開業` と `中止` は対象外（終わった話なので動かない）。**`凍結` は対象に含める** — 凍結は終わりではなく再開しうるが、再開の発表を拾えるのは調査だけなので、キューから外すと再開に気づく経路がなくなる。

**1 セッションで扱うのはこの 10 件だけ。** WebSearch の回数上限は**ターンではなく Claude Code のセッション単位**なので、対象を全件調べようとすると途中で使い切って、どこまで終わったのか分からない状態で止まる。少しずつ調べてキューを進め、**セッションを分けて繰り返し一周させる**設計にしている。1 回で終わらせようとしない。

**調査は 1 セッションに 1 回だけ。** 10 件を終えたら 2 バッチ目を始めない（依頼されても同じ）。上限がセッション単位なので 2 回目は 1 回目の残りで走ることになり、その残量を知る手段がない。収まるか判断できないまま始めて途中で枯渇すると、その回の調査が無駄になる。**続きは新しいセッションで行う**（セッションを分け直すコストはほぼゼロで、賭けに負けたときのコストだけが大きい）。

調べる駅を名指しされたときは、古い順ではなくその駅を調べる。**1 セッション 10 件の上限は同じ** — 検索の上限は誰が対象を選んだかに関係なく効く。超える分は次のセッションに回し、残した駅を最終応答に列挙する（名指しの駅はキューの順番に乗らないので、書き残さないと次に何を調べるべきか分からなくなる）。

出力は JSON なので、一覧を眺めるだけなら `| jq -r '.[] | [.checked_on, .status, .pref, .city, .name, .date] | @tsv'` を足す（`--silent` を落とすと npm のバナーが stdout に混ざって jq が読めなくなる）。

## 2. 駅ごとに調べて書く

**1 駅ずつ閉じてから次へ移る。** 調べる → 値を決める → `npm run plan` で書く、までをその駅で終わらせる。10 件分の検索結果とページ本文を抱えたまま進まずに済む — 書く前にコンテキストが尽きると、そこまでに使った検索がまるごと無駄になる。

**新しい情報がなかった駅にもコマンドを 1 回撃つ。** 撃たないとその駅は調査済みにならず、次のセッションでまた引かれる。

**逆に、調べていない駅にはコマンドを撃たない。** 調査済みとしてキューの最後尾に回ってしまう。10 件に届かないまま終えるなら、調べた分だけ撃って残りは次のセッションに回す。

コミットと PR は全件終えてから 1 回だけ（§3）。書き込みはローカルのファイル操作なので、駅ごとに書いても外に何も出ない。

### 検索クエリの組み立て

**`city` から郡名を除去する。** 郡名を含めると検索がヒットしない。

- `上伊那郡箕輪町` → `箕輪町`
- `高岡郡佐川町` → `佐川町`
- `さいたま市岩槻区` → そのまま（政令市の区は地名として機能する）

**`pref` を必ず含める。** 市町村名だけだと同名地名を拾う（「白石市」の検索で札幌市白石区が上位に来る）。

**`name` が仮称でなければ `name` で検索する。** 「道の駅 ◯◯市」「道の駅 ◯◯町」の形は仮称なので `city` で検索する。「みのわテラス」「くるん熊谷」のような固有名は、それ自体で検索した方がはるかに精度が高い。

```
道の駅 {pref} {city} 開業        ← 仮称の場合
{name} 開業 いつ                  ← 固有名がある場合
```

### 既存の道の駅と取り違えない

1 つの市区町村に道の駅が複数あることは珍しくない（南房総市には 8 駅、高山市にも 8 駅ある）。検索すると、その市区町村に既にある駅の記事が上位に来る。

調べているのは**新設・再整備の計画**なので、既存駅の話だと分かれば読み飛ばす。対象の市区町村にどんな駅があるかを、調査を始める前に引いておく:

```bash
grep "南房総市" data/stations.csv | cut -f3   # リポジトリルートで実行する
```

`data/stations.csv` は michi-no-eki.jp のスクレイピング結果（拡張子に反して TSV）で、既存駅を引く用途に使う。**ただし登録済みかどうかの判定には使えない。** 登録されても掲載が遅れることがあるので、載っていないことは未登録の根拠にならない。

地名が似た別の駅が紛れ込むこともある（南アルプス市を調べると、長野県伊那市の「南アルプスむら長谷」が出てくる）。判断に迷ったら所在地と開業時期を見る。既に開業している駅の記事なら、調査対象ではない。

### 記事の日付は自分で確かめる

検索結果は新しい順には並ばず、数年前の記事が最上位に来る。**WebSearch は `after:` などの検索演算子を解釈しないので、クエリ側で期間を絞ることはできない。**

**開いて日付を確認してから判断の材料にする。** 古い記事しか出てこなければ「進捗なし」の根拠になる。日付が書かれていないページ（まとめサイトに多い）はいつの情報か分からないので、根拠にしない。

### 出典の優先順位

1. **自治体の公式サイト** — 一次情報。ただし更新が遅く、決定済みの情報が載っていないこともある
2. **地方紙・地方建設業紙** — 開業日の速報はここが早い。優先交渉権者の決定なども載る
3. **国交省・地方整備局** — 登録の確定情報
4. まとめサイト・個人ブログ — 古い情報が残りがちなので、他に裏が取れないときの補助に留める

**同じ順位の出典が同じ内容を報じているなら、全文が読める無料記事を優先する。** 地方紙は本文の途中から有料会員限定になることが多く、有料記事を `urls` に置くと後から根拠を辿る人が確かめられない。判断の材料としても弱い — 肝心の開業日が有料部分にあることがある。

ただし**この優先は順位をまたがない。** 無料のまとめサイトが有料の地方紙を追い越すことはない（4 位が 2 位より上にはならない）。無料の代替を求めて追加の検索もしない — 手元の検索結果に無ければ有料記事を出典にする。

### 既存の出典を点検する

調査する駅の `urls` にある URL は、**その駅を調べるついでに開いて生きているかを確かめる。** 出典は時間が経つと消える（地方紙は数ヶ月から数年で記事を落とす）ので、点検しないと台帳のリンクが少しずつ死んでいく。

- **404・記事削除だったら代替を探す。** 同じ発表を報じた別の記事か、自治体の公式ページを検索する
    - 見つかったら**差し替える**（古い URL を消して新しいものを書く）
    - 見つからなければ**削除してよい**
    - **ただし削除すると `urls` が 0 件になる場合は残す**（以下「0 件ガード」）。根拠が 1 つもないレコードにするより、辿れない URL が残っている方がまし（Web アーカイブから拾える余地がある）
    - ガードは本数しか見ないので、**消す 1 本がマスタの `date` / `status` / `name` の唯一の根拠だったかはここで判断する。** そうなら `docs/plan-reports.md` に載せる（消すのをやめる条件は本数のままで、値ごとの判断は人に渡す）
    - 代替のない死んだリンクが複数あって**どれか 1 本を残すことになったら、公開日の新しい方を残す** → 開けないページで公開日が分からなければ「出典の優先順位」が上の 1 本 → それも同じなら後ろの要素。**配列の位置は最後の手段**にする — 差し替えは要素をその位置で上書きするので、後ろの要素が新しいとは限らない（「urls は 10 件まで」の採点表はここでは使えない — 開けないページは「内容」と「新しさ」を採点できない）
- **新しい版に置き換わっていた場合も差し替えてよい。** 「開業日決定」の記事が「開業しました」の記事になった、自治体が計画ページを更新した、などで古い URL を持ち続ける理由はない。同じことを二重に持たない
- **200 が返っても中身が別物なら実質リンク切れ。** 記事が消えてトップページや「お探しのページは見つかりません」に飛ばされるパターンがあるので、ステータスではなく開いた中身で判断する
- **有料記事はリンク切れではない。** 購読の案内ページに誘導されても記事自体は生きているので、差し替え・削除の対象にしない（有料記事を出典として許容するのは上記のとおり）

この点検は 1 駅あたりの取得回数を既存リンクの本数だけ増やす。§1 の 10 件は**検索**の上限から来た数なので、点検そのものでは目減りしない — 減るのは代替探しの検索が発生した駅の分だけ。10 件に届かなくなったときの畳み方は §2 冒頭にある。

### 自治体ページの中身は PDF のことが多い

一覧ページを開いても概要しか書いておらず、日程は添付 PDF にある、というパターンが頻出する。ページを WebFetch して「添付 PDF へのリンクを URL ごと列挙して」と指示すればリンクを拾える。

Bash のサンドボックスは許可ホストにしかネットワークを通さないので、`curl -s "<url>" | grep -oE 'href="[^"]*\.pdf"'` が通るとは限らない。試すのは自由だが、弾かれたら WebFetch に切り替える。

拾った PDF を WebFetch にかける。ただし**画像 PDF はこの環境ではテキスト化できない**（`pdftoppm` が入っていない）。読めなければ深追いせず、同じ内容を報じた記事を探す方が早い。

### 書く値: date

マスタは**判明している粒度をそのまま記録する**列で、`2026-09-18` も `2026` も `2026夏` も等しく正しい値。**変換してよいのは和暦 → 西暦だけで、それ以外は出典の言葉をそのまま写す。**

| 出典の表現 | 書く値 | |
|---|---|---|
| 令和 9 年 7 月オープン | `2027-07` | 月まで言い切っているので日付形式にできる |
| 令和 9 年度初頭 | `2027年度初頭` | ✗ `2027-04` — 「初頭」が何月かは出典が言っていない |
| 令和 9 年夏ごろ | `2027夏ごろ` | ✗ `2027-07` |
| 2028 年度 | `2028年度` | ✗ `2028` — 年度は 2029 年 3 月まで含む |
| 2026 年度下半期 | `2026年度下半期` | ✗ `2026` — 暦年をまたぐ |

「初頭」「上半期」「ごろ」を月に置き換えるのは、出典にない情報を足す行為で、**後から見たときに確定情報と区別がつかなくなる**。これがこの列でいちばん避けたい壊れ方なので、粒度を上げる方向にも下げる方向にも丸めない。

日本語混じりの表記で地図が壊れるものはない。`計画中(予定あり)` / `計画中(未定)` の振り分けは `date` の有無だけで決まり（`src/frontend/types/plan.ts`）、サイドバーの並び順は粒度混在を前提に組んである（`src/frontend/plan-order.ts`）。

年度と暦年の区別だけは意識しておく — 「令和 9 年度」は 2027 年 4 月〜2028 年 3 月であって 2027 年ではない。ただし気づいたからといって暦年に直すのではなく、年度のまま書く。

#### 開業が近いものは「延期」を疑う

`date` が 1〜2 年以内のレコードでは、**開業日が前倒しで確定するより延期される方が多い**。自治体は延期を「開業時期の延期について」のような専用ページで公表するので、既存の `date` を裏付ける情報だけで満足せず、より新しい発表がないか確認する。

### 書く値: status

`計画中` / `登録済み` / `開業` / `凍結` / `中止` の 5 値のみ。

**登録は必ずニュースになる。** 国交省の登録は年 2 回（6 月・12 月）にまとまって公示され、登録証の交付は自治体の発表や地方紙の記事になる。自治体が「登録を目指す」と書いているだけでは `計画中` のまま。

**`開業` への変更は、実際に開いたことが確認できたときだけ。** 確認が取れないうちは動かさない — `開業` にした駅は §1 の抽出から外れるので、誤って倒すと人が手で戻すまで二度と調査キューに乗らない。「開業しました」の記事を見つけたら、それが調査対象の駅の話か確かめる（「既存の道の駅と取り違えない」）。

**`凍結` と `中止` は、自治体がそう宣言したときだけ。** どちらに入れるかは**計画が終わったと言っているか**で分ける:

| 発表の言葉 | 書く値 | |
|---|---|---|
| 凍結・休止・一時中断 | `凍結` | 止まっているだけで、再開しうる |
| 中止・白紙撤回・断念・見送り・廃止 | `中止` | 終わったと言っている |
| 延期 | どちらでもない | 日程が動いただけなので `date` を書き換える（「開業が近いものは『延期』を疑う」） |

**この言葉が出るまでは `status` を現在値のまま動かさない。** **`登録済み` の駅を `計画中` に落とすのも同じく禁止** — 調査対象には `登録済み` も入るので、疑いを理由に登録の確定情報を巻き戻さない。中止や凍結を**疑わせる**材料はいくらでも出てくる — 数年間更新がない、予算が計上されなくなった、公式ページが消えた、推進していた首長が交代した — が、どれも根拠にはならない。疑いの段階で `中止` を書くと、生きている計画を終わった話として台帳から消すことになる。**`凍結` も疑いの逃げ場ではない** — 動いていないように見えることは `凍結` の根拠でもない。

`凍結` の駅は §1 の調査対象に残るので、再開が発表されたら `計画中` に戻し、中止が宣言されたら `中止` に倒す。

### 書く値: name

正式名称や愛称が判明したら変更する（「道の駅 石川町」に対して正式名称が「道の駅石川」、仮称だった駅に「うぇるかぶ」のような愛称が決まった、など）。

**表記は出典の正式名称をそのまま写す。** `date` と同じ考え方で、台帳の体裁に合わせて空白を足したり削ったりしない。ただし `(移転)` `(再整備)` はこの台帳独自の区別で正式名称の一部ではないので、改名しても残す。

`name` は一意ではない（「道の駅 川崎町」が福岡県と宮城県にある）。レコードの同定が `name` + `pref` なので、**改名で同じ `pref` の中に同じ `name` を作らない。**

### 書く値: pref / city

所在地が実際と違うと気づいたら**修正する**。ただし所在地が特定できず「どちらが正しいか分からない」なら、直さずに `docs/plan-reports.md` に載せる。

`pref` と `city` は **`data/cities.json` にある表記で書く**（`city` は `上伊那郡箕輪町` のように郡名を含む形、政令市は `さいたま市岩槻区` のように区まで）。**`cities.json` に無い市区町村は書かない。**

引き当たらないときは、まず**郡名の欠落と政令市の区**を疑う（`箕輪町` ではなく `上伊那郡箕輪町`、`さいたま市` ではなく `さいたま市岩槻区`）。

それでも無いなら（改称・合併・分割に `cities.json` が追随していない）、**その所在地を含む市区町村を `cities.json` から選んで書いて進める**（改称なら旧称、合併なら合併前のどれか — 座標が落ちる先になるので、その場所を含む方を選ぶ）。`cities.json` は別の作業で更新するので、**調査セッションは触らない。** 気づいた古さは `docs/plan-reports.md` に申し送る（「列に書けないことは `docs/plan-reports.md` に追記する」）。

所在地を触っていないのに `Unknown municipality` で落ちたときは、そのレコードの `city` が `cities.json` に無い表記になっている。`--city` に `cities.json` にある表記を渡して直す。

### 書く値: urls

出典リンクの配列で、要素は `{"title": "...", "url": "..."}`（キー順も固定）。4 つの操作がある。対象の URL は**完全一致**で選ぶので、`show`（「現在値を読む」）の出力からコピーする:

```bash
# 足す（空きがあるとき）
npm run plan -- url add "道の駅 石川町" 福島県 --url='https://example.jp/news/456' --title='道の駅◯◯ 開業日決定'

# 差し替える（リンク切れに代替を当てる / 10 件のレコードで 1 本入れ替える）
npm run plan -- url replace "道の駅 川崎町" 福岡県 \
    --dead='https://dead.example.jp/a' --url='https://example.jp/news/456' --title='道の駅◯◯ 開業しました'

# 消す（代替のないリンク切れ）
npm run plan -- url remove "道の駅 川崎町" 福岡県 --dead='https://dead.example.jp/a'

# タイトルだけ入れる（点検で見た見出しを写す）
npm run plan -- url title "道の駅 川崎町" 福岡県 --url='https://example.jp/plan' --title='◯◯町 道の駅整備基本計画'
```

**値はシェルの単一引用符で囲む。** `?` や `&` を含む URL がそのまま渡る。値に `'` が含まれるなら `'\''` で閉じ直す（囲みを閉じ忘れると bash が入力待ちになって、原因が分かりにくい）。

選ぶ基準は「後から根拠を辿れるか」で、同じことを言っている記事を何本も足す必要はない。足すだけでなく、点検（「既存の出典を点検する」）で 404 や差し替えが分かったリンクは `url remove` / `url replace` の対象になる。

**リンクだけを置く列で、地の文の置き場所ではない。** 「着工は未定」のような補足は書かない — 状況を表すのは `status` と `date` で、この列が答えるのは「その値の根拠はどこにあるか」だけ。判明したが列に書けないことは `docs/plan-reports.md` に回す（「列に書けないことは `docs/plan-reports.md` に追記する」）。

**`title` は出典ページの見出しをそのまま写す。** 地図はこれをリンクのラベルとして描画するので、URL だけが並ぶと何のページか分からない。**点検で開いたページの見出しは `title` に写し直してよい。** 点検でページを開くのでタイトルは手元にあり、直すのに追加の取得は要らない。義務ではないので、他に書くことがない駅で `urls` を動かすためにやる必要はない。

**`title` を空（や空白だけ）にしない。** 地図はこれをリンクのラベルにするので、空だと押せないリンクが並ぶ。

#### urls は 10 件まで

`urls` は 1 レコード 10 件が上限（上限を置く理由は CLAUDE.md「開発計画マスタ」）。**10 件に達しているレコードに出典を足すなら、いちばん弱い 1 本を落として入れ替える。**

点検（「既存の出典を点検する」）を先に済ませる。代替のない 404 の削除や、旧版と重複した URL の解消で空きが出れば、入れ替えは要らなくなる。

足す URL は開いて中身を確かめてから入れ替えにかける（開けなければ足さない）。既存の 10 本のうち**現在値の唯一の根拠は落とす候補から外す** — その 1 本を消すと `date` / `status` / `name` が何を見て決まったのか辿れなくなるので、別の 1 本を落とす（唯一の根拠は 3 列分しかありえないので、10 本のうち 7 本以上は必ず候補に残る）。**足すのをやめてよいのは、今回値を動かしていない補強の記事だけ** — 書き換えた `date` / `status` / `name` の根拠は `urls` に入れる。**0 件ガードとは違う判断** — あちらは代替のない死んだリンクを前に本数しか見ない（値ごとの判断は人に渡す）が、ここでは落とす 1 本を選べるので、根拠として要るかどうかを見る。

残りは**足す 1 本も同じ表で採点して**比べ、合計のいちばん低い 1 本を落とす。落ちるのが足す 1 本なら入れ替えず、そのまま足さない（ただし今回書き換えた値の根拠なら、既存 10 本のうち候補に残っているいちばん低い 1 本を落とす — 根拠を外に置いたレコードは作らない）:

| 観点 | 加点 |
|---|---|
| 情報ソース | 「出典の優先順位」の 1 位 +4 / 2 位 +3 / 3 位 +2 / 4 位 +1 |
| 内容 | 開業日・開業予定が書かれている +3 / 整備や開業が動いた発表（着工、契約、登録、延期） +2 / 開業スケジュールに影響しない進捗報告 +0 |
| 新しさ | 調査日から 1 年以内 +2 / 3 年以内 +1 / それ以前 +0 / 公開日が分からない +0 |

同点で**情報ソースの加点も同じ**なら全文無料の方を残す（無料の優先は「出典の優先順位」のとおり順位をまたがないので、同順位の中だけで効かせる）。それでも決まらなければ公開日の古い方を落とす — 公開日が分からないものはいちばん古い扱いにする（いつの情報か分からないページは根拠にしない。「記事の日付は自分で確かめる」）。

**内容と新しさでは順位が逆転しうる** — 何年も前の公式ページより、開業日を報じた先月の地方紙の方が今の値の根拠になる。

入れ替えは `url replace` で行う（落とす 1 本の URL を `--dead` に、足す 1 本を `--url` / `--title` に渡す）。**足す出典が 2 本以上あるなら、1 本ずつ採点 → 差し替えを繰り返す** — まとめて足すと 10 件を超える。

### `npm run plan` で書き換える

マスタの書き換えは `npm run plan` で行う。

駅は `name` と `pref` で指定する。名前に空白が含まれるので**クオートする**。

```bash
npm run plan -- update "道の駅 石川町" 福島県 --date=2026-09-18 --status=登録済み
```

フラグと列の対応（それぞれの値をどう決めるかは上の「書く値: …」の各節）:

| フラグ | 備考 |
|---|---|
| `--status=` | 5 値のみ |
| `--date=` | 自由テキスト。検証しない |
| `--name=` | 改名。旧名で引いて新しい名前を渡す |
| `--pref=` / `--city=` | 所在地の修正。`data/cities.json` にある表記のみ。**県をまたぐ修正では両方渡す** — 片方だけ変えると `cities.json` に無い組み合わせになる |
| `--lat=` / `--lng=` | 数値。空（`--lat=`）で「座標なし」に戻す |

**フラグを 1 つも渡さない `update` が「調べたが変更はなかった」の記録になる。**

```bash
npm run plan -- update "道の駅 共和町" 北海道
```

書き終えたら **`git diff data/plans.json` で確かめる。** 意図したレコードだけが動いていることを見る。差分がそのままレビューに出るので、この確認は PR の準備でもある。

### 現在値を読む

書き換える前に、その駅の現在値を見る。とくに `urls` を触るときは、同じ出典が既にないか・どの URL が対象かをここで確かめる:

```bash
npm run --silent plan -- show "道の駅 川崎町" 福岡県
```

出力は JSON なので、`urls` だけ見たいなら `| jq -r '.urls[] | [.title, .url] | @tsv'` を足す。

### レコードを追加する

台帳にない駅が見つかったら追加する。**出典を 1 本必ず指定する**（根拠のないレコードを足さない）。

```bash
npm run plan -- add --name='道の駅 ◯◯町' --pref=福井県 --city='◯◯郡◯◯町' --status=計画中 \
    --date=2028年度 --url='https://example.jp/news' --title='◯◯町に道の駅を整備へ'
```

**座標は分かるなら `--lat` / `--lng` に書く。** 分からなければ省略してよい（`city` から市区町村の代表点に落ちる）。

**重複に注意する。** 既存の仮称（「道の駅 ◯◯町」）と正式名称が同じ駅を指していることがある。追加の前にその県の駅を眺める:

```bash
npm run --silent plan -- list | jq -r '.[] | select(.pref == "福井県") | .name'
```

仮称と正式名称は別の文字列なので、同じ駅を二重に登録しないよう目で見て突き合わせる。

### 列に書けないことは `docs/plan-reports.md` に追記する

**メンテナが判断しないと先に進めないもの、または調査でしか気づけず台帳の外を直さないと解決しないもの**（後者は現在 `cities.json` の古さだけ）**を書く。** 調べた結果 `status` や `date` を動かさなかったこと自体は書かない — 中止や凍結を疑ったが宣言は見つからなかった、という否定的な結果もこれに含む（「書く値: status」）。これは値を動かさなかったすべての駅で成立するので、書き始めると報告が調査ログになる。同じ検索は次の調査でもう一度できるし、調べた跡は差分に残る。

**末尾に追記するだけで、既存の項目には触らない** — 対応と消し込みは人が行うので、前回までの項目を読んで判断する必要はない。

書くのは、人に渡さないと片付かないもの:

- **資料が食い違って値を確定できない** — 所在地が市の資料と県の資料で違う（「書く値: pref / city」）
- **現在値の根拠がデータから消えた** — 代替が見つからず 0 件ガードで残したリンク切れ、消したリンクが `date` / `status` / `name` の唯一の根拠だった（「既存の出典を点検する」）。レコードを見ただけでは分からない（リンクは残っているので、開くまで死んでいると気づけない）
- **`cities.json` が実世界に追随していない** — 改称・合併・分割で、現在の市区町村名が `data/cities.json` に無い（「書く値: pref / city」）。`city` は載っている表記で書いて進めたうえで報告する。`cities.json` の更新は別の作業なので、伝えないと直らない

**1 駅 1 項目、文単位で完結させる。** 日付・駅名・都道府県を頭に置く。日付は**書き込みコマンドが出力する JST の当日を写す** — 素の `date` はマシンのタイムゾーンで決まるので、UTC のマシンでは JST 午前中に前日が入り、同じ調査の記録が台帳と 1 日食い違う:

```markdown
- **2026-08-11 道の駅◯◯（福井県）** — 市の資料では △△町、県の資料では ×× 町とあり `city` を確定できない。[出典](https://example.com/)
```

**自分で直せることは書かない。** `pref` / `city` の明らかな誤りは直して差分に含める。

## 3. コミットして PR を出す

### lint と test を通す

```bash
npm run lint:fix
npm test
```

### PR

**1 セッション 1 PR。** 調べた分をまとめて 1 本にする。コミットログは英語で、「何を変更したか」と「その結果何が達成されたか」を書く。

**PR 本文に書くのは 2 つだけ。**

1. **調査した駅の一覧** — 何を調べたか。値が動かなかった駅も含める（差分は 1 行だけになる）
2. **報告事項** — `docs/plan-reports.md` に追記した内容

**更新したレコードは書かない。** 何をどう変えたかは `data/plans.json` の差分に出ており、その根拠は `urls` のリンクとして差分に入っている。本文で繰り返すと、差分と食い違ったときにどちらが正しいか分からなくなる。

それ以外に伝えたいことがあればコミットメッセージに書く。

### 締めにキューの残りを報告する

最終応答には、差分にもコミットにも出ないものを書く。

1. **キューの残り** — 1 回では一周しないので、次のセッションを走らせるべきかの判断材料になる
2. **持ち越した駅** — 名指しされて 10 件に収まらなかった駅（キューの順番に乗らないので、書かないと次に何を調べるべきか分からなくなる）

キューは**全件書き終えてから数える** — 先に数えると、今調べた 10 件が古いままの側に入る。

数えるのは §1 と同じ対象なので、同じ `list` の出力を jq で集計する:

```bash
npm run --silent plan -- list --status=登録済み,計画中,凍結 --sort=checked_on \
  | jq '(.[0].checked_on) as $oldest
        | {total: length,
           oldest: $oldest,
           at_oldest: ([.[] | select(.checked_on == $oldest)] | length)}'
```

> 対象は全 ◯◯ 件。いちばん古い調査日は YYYY-MM-DD で ◯◯ 件。

`at_oldest` は最古の調査日を共有する件数で、ここが 10 件ずつ削られていくことで一周が進む。

`oldest` がまだ古いなら「続きは新しいセッションで」を添える。全件が十分に新しければ足さない — 一周し終わった直後にもう一度走らせても、いちばん新しい駅を調べ直すだけになる。
