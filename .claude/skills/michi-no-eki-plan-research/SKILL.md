# 道の駅 整備計画データの調査・更新

開発計画マスタ `data/plans.json` の `status` / `date` / `name` / `urls` を Web 調査で最新化する。

## 全体の流れ

1. 対象を取り出す — `checked_on` の古い順に 10 件
2. 駅ごとに調べて書く — 1 駅を調べ、値を決め、その場で `data/plans.json` に書いてから次へ移る
3. コミットして PR を出す

番号は以降の節に対応する。

## 1. 対象を取り出す

対象は `data/plans.json`（リポジトリルートからの相対パス）から選ぶ。`checked_on`（最後に調査した日）が古い順に 10 件だけ取る。

```bash
jq '[.[] | select(.status == "登録済み" or .status == "計画中" or .status == "凍結")] | sort_by(.checked_on) | .[:10]' data/plans.json
```

`開業` と `中止` は対象外（終わった話なので動かない）。**`凍結` は対象に含める** — 凍結は終わりではなく再開しうるが、再開の発表を拾えるのは調査だけなので、キューから外すと再開に気づく経路がなくなる。

**1 セッションで扱うのはこの 10 件だけ。** WebSearch の回数上限は**ターンではなく Claude Code のセッション単位**なので、対象を全件調べようとすると途中で使い切って、どこまで終わったのか分からない状態で止まる。少しずつ調べて `checked_on` を進め、**セッションを分けて繰り返し一周させる**設計にしている。1 回で終わらせようとしない。

**調査は 1 セッションに 1 回だけ。** 10 件を終えたら 2 バッチ目を始めない（依頼されても同じ）。上限がセッション単位なので 2 回目は 1 回目の残りで走ることになり、その残量を知る手段がない。収まるか判断できないまま始めて途中で枯渇すると、その回の調査が無駄になる。**続きは新しいセッションで行う**（セッションを分け直すコストはほぼゼロで、賭けに負けたときのコストだけが大きい）。

調べる駅を名指しされたときは、古い順ではなくその駅を調べる。**1 セッション 10 件の上限は同じ** — 検索の上限は誰が対象を選んだかに関係なく効く。超える分は次のセッションに回し、残した駅を最終応答に列挙する（名指しの駅はキューの順番に乗らないので、書き残さないと次に何を調べるべきか分からなくなる）。

一覧を眺めるだけなら `| jq -r '.[] | [.checked_on, .status, .pref, .city, .name, .date] | @tsv'` を足す。

## 2. 駅ごとに調べて書く

**1 駅ずつ閉じてから次へ移る。** 調べる → 値を決める → `data/plans.json` に書く → `checked_on` を押す、までをその駅で終わらせる。10 件分の検索結果とページ本文を抱えたまま進まずに済む — 書く前にコンテキストが尽きると、そこまでに使った検索がまるごと無駄になる。

**新しい情報がなかった駅も `checked_on` だけは押す。** 取りこぼすとその駅は調査済みにならず、次のセッションでまた引かれる。

コミットと PR は全件終えてから 1 回だけ（§3）。書き込みはローカルのファイル操作なので、駅ごとに書いても外に何も出ない。

### 検索クエリの組み立て

**`city` から郡名を除去する。** 郡名を含めると検索がヒットしない。

- `上伊那郡箕輪町` → `箕輪町`
- `高岡郡佐川町` → `佐川町`
- `さいたま市岩槻区` → そのまま（政令市の区は地名として機能する）

**`pref` を必ず含める。** 市町村名だけだと同名地名を拾う（「白石市」の検索で札幌市白石区が上位に来る）。

**`name` が仮称でなければ `name` で検索する。** 「道の駅 ◯◯市」「道の駅 ◯◯町」の形は仮称なので `city` で検索する。「みのわテラス」「くるん熊谷」のような固有名は、それ自体で検索した方がはるかに精度が高い。

```
道の駅 {pref} {city} 開業        ← 仮称の場合
{name} 開業 いつ                  ← 固有名がある場合
```

### 既存の道の駅と取り違えない

1 つの市区町村に道の駅が複数あることは珍しくない（南房総市には 8 駅、高山市にも 8 駅ある）。検索すると、その市区町村に既にある駅の記事が上位に来る。

調べているのは**新設・再整備の計画**なので、既存駅の話だと分かれば読み飛ばす。対象の市区町村にどんな駅があるかを、調査を始める前に引いておく:

```bash
grep "南房総市" data/stations.csv | cut -f3   # リポジトリルートで実行する
```

`data/stations.csv` は michi-no-eki.jp のスクレイピング結果（拡張子に反して TSV）で、既存駅を引く用途に使う。**ただし登録済みかどうかの判定には使えない。** 登録されても掲載が遅れることがあるので、載っていないことは未登録の根拠にならない。

地名が似た別の駅が紛れ込むこともある（南アルプス市を調べると、長野県伊那市の「南アルプスむら長谷」が出てくる）。判断に迷ったら所在地と開業時期を見る。既に開業している駅の記事なら、調査対象ではない。

### 記事の日付は自分で確かめる

検索結果は新しい順には並ばず、数年前の記事が最上位に来る。**WebSearch は `after:` などの検索演算子を解釈しないので、クエリ側で期間を絞ることはできない。**

**開いて日付を確認してから判断の材料にする。** 古い記事しか出てこなければ「進捗なし」の根拠になる。日付が書かれていないページ（まとめサイトに多い）はいつの情報か分からないので、根拠にしない。

### 出典の優先順位

1. **自治体の公式サイト** — 一次情報。ただし更新が遅く、決定済みの情報が載っていないこともある
2. **地方紙・地方建設業紙** — 開業日の速報はここが早い。優先交渉権者の決定なども載る
3. **国交省・地方整備局** — 登録の確定情報
4. まとめサイト・個人ブログ — 古い情報が残りがちなので、他に裏が取れないときの補助に留める

**同じ順位の出典が同じ内容を報じているなら、全文が読める無料記事を優先する。** 地方紙は本文の途中から有料会員限定になることが多く、有料記事を `urls` に置くと後から根拠を辿る人が確かめられない。判断の材料としても弱い — 肝心の開業日が有料部分にあることがある。

ただし**この優先は順位をまたがない。** 無料のまとめサイトが有料の地方紙を追い越すことはない（4 位が 2 位より上にはならない）。無料の代替を求めて追加の検索もしない — 手元の検索結果に無ければ有料記事を出典にする。

### 既存の出典を点検する

調査する駅の `urls` にある URL は、**その駅を調べるついでに開いて生きているかを確かめる。** 出典は時間が経つと消える（地方紙は数ヶ月から数年で記事を落とす）ので、点検しないと台帳のリンクが少しずつ死んでいく。

- **404・記事削除だったら代替を探す。** 同じ発表を報じた別の記事か、自治体の公式ページを検索する
    - 見つかったら**差し替える**（古い URL を消して新しいものを書く）
    - 見つからなければ**削除してよい**
    - **ただし削除すると `urls` が 0 件になる場合は残す**（以下「0 件ガード」）。根拠が 1 つもないレコードにするより、辿れない URL が残っている方がまし（Web アーカイブから拾える余地がある）
    - ガードは本数しか見ないので、**消す 1 本がマスタの `date` / `status` / `name` の唯一の根拠だったかはここで判断する。** そうなら `docs/plan-reports.md` に載せる（消すのをやめる条件は本数のままで、値ごとの判断は人に渡す）
- **新しい版に置き換わっていた場合も差し替えてよい。** 「開業日決定」の記事が「開業しました」の記事になった、自治体が計画ページを更新した、などで古い URL を持ち続ける理由はない。同じことを二重に持たない
- **200 が返っても中身が別物なら実質リンク切れ。** 記事が消えてトップページや「お探しのページは見つかりません」に飛ばされるパターンがあるので、ステータスではなく開いた中身で判断する
- **有料記事はリンク切れではない。** 購読の案内ページに誘導されても記事自体は生きているので、差し替え・削除の対象にしない（有料記事を出典として許容するのは上記のとおり）

この点検は 1 駅あたりの取得回数を既存リンクの本数だけ増やす。§1 の 10 件は**検索**の上限から来た数なので、点検そのものでは目減りしない — 減るのは代替探しの検索が発生した駅の分だけ。10 件に届かなくなったときの畳み方は後述の「`checked_on` を押す」にある。

### 自治体ページの中身は PDF のことが多い

一覧ページを開いても概要しか書いておらず、日程は添付 PDF にある、というパターンが頻出する。ページを WebFetch して「添付 PDF へのリンクを URL ごと列挙して」と指示すればリンクを拾える。

Bash のサンドボックスは許可ホストにしかネットワークを通さないので、`curl -s "<url>" | grep -oE 'href="[^"]*\.pdf"'` が通るとは限らない。試すのは自由だが、弾かれたら WebFetch に切り替える。

拾った PDF を WebFetch にかける。ただし**画像 PDF はこの環境ではテキスト化できない**（`pdftoppm` が入っていない）。読めなければ深追いせず、同じ内容を報じた記事を探す方が早い。

### 書く値: date

マスタは**判明している粒度をそのまま記録する**列で、`2026-09-18` も `2026` も `2026夏` も等しく正しい値。**変換してよいのは和暦 → 西暦だけで、それ以外は出典の言葉をそのまま写す。**

| 出典の表現 | 書く値 | |
|---|---|---|
| 令和 9 年 7 月オープン | `2027-07` | 月まで言い切っているので日付形式にできる |
| 令和 9 年度初頭 | `2027年度初頭` | ✗ `2027-04` — 「初頭」が何月かは出典が言っていない |
| 令和 9 年夏ごろ | `2027夏ごろ` | ✗ `2027-07` |
| 2028 年度 | `2028年度` | ✗ `2028` — 年度は 2029 年 3 月まで含む |
| 2026 年度下半期 | `2026年度下半期` | ✗ `2026` — 暦年をまたぐ |

「初頭」「上半期」「ごろ」を月に置き換えるのは、出典にない情報を足す行為で、**後から見たときに確定情報と区別がつかなくなる**。これがこの列でいちばん避けたい壊れ方なので、粒度を上げる方向にも下げる方向にも丸めない。

日本語混じりの表記で地図が壊れるものはない。`計画中(予定あり)` / `計画中(未定)` の振り分けは `date` の有無だけで決まり（`src/frontend/types/plan.ts`）、サイドバーの並び順は粒度混在を前提に組んである（`src/frontend/plan-order.ts`）。

年度と暦年の区別だけは意識しておく — 「令和 9 年度」は 2027 年 4 月〜2028 年 3 月であって 2027 年ではない。ただし気づいたからといって暦年に直すのではなく、年度のまま書く。

#### 開業が近いものは「延期」を疑う

`date` が 1〜2 年以内のレコードでは、**開業日が前倒しで確定するより延期される方が多い**。自治体は延期を「開業時期の延期について」のような専用ページで公表するので、既存の `date` を裏付ける情報だけで満足せず、より新しい発表がないか確認する。

延期の告知には「最終的な時期は◯月ごろ公表予定」と続きが予告されていることがある。見つけたら `docs/plan-reports.md` に書く — いつ再調査すべきかの判断材料になる。

### 書く値: status

`計画中` / `登録済み` / `開業` / `凍結` / `中止` の 5 値のみ。**これ以外を書くと `npm run ci` が落ちる**（`src/frontend/plan-data.test.ts`）。

**登録は必ずニュースになる。** 国交省の登録は年 2 回（6 月・12 月）にまとまって公示され、登録証の交付は自治体の発表や地方紙の記事になる。自治体が「登録を目指す」と書いているだけでは `計画中` のまま。

**`開業` への変更は、実際に開いたことが確認できたときだけ。** 確認が取れないうちは動かさない — `開業` にした駅は §1 の抽出から外れるので、誤って倒すと人が手で戻すまで二度と調査キューに乗らない。「開業しました」の記事を見つけたら、それが調査対象の駅の話か確かめる（「既存の道の駅と取り違えない」）。

**`凍結` と `中止` は、自治体がそう宣言したときだけ。** どちらに入れるかは**計画が終わったと言っているか**で分ける:

| 発表の言葉 | 書く値 | |
|---|---|---|
| 凍結・休止・一時中断 | `凍結` | 止まっているだけで、再開しうる |
| 中止・白紙撤回・断念・見送り・廃止 | `中止` | 終わったと言っている |
| 延期 | どちらでもない | 日程が動いただけなので `date` を書き換える（「開業が近いものは『延期』を疑う」） |

**この言葉が出るまでは `status` を現在値のまま動かさない。** **`登録済み` の駅を `計画中` に落とすのも同じく禁止** — 調査対象には `登録済み` も入るので、疑いを理由に登録の確定情報を巻き戻さない。中止や凍結を**疑わせる**材料はいくらでも出てくる — 数年間更新がない、予算が計上されなくなった、公式ページが消えた、推進していた首長が交代した — が、どれも根拠にはならない。疑いの段階で `中止` を書くと、生きている計画を終わった話として台帳から消すことになる。**`凍結` も疑いの逃げ場ではない** — 動いていないように見えることは `凍結` の根拠でもない。**疑いを持ったこと自体は `docs/plan-reports.md` に書く** — どちらに倒すかは人が判断できる。

`凍結` の駅は §1 の調査対象に残るので、再開が発表されたら `計画中` に戻し、中止が宣言されたら `中止` に倒す。

### 書く値: name

正式名称や愛称が判明したら変更する（「道の駅 石川町」に対して正式名称が「道の駅石川」、仮称だった駅に「うぇるかぶ」のような愛称が決まった、など）。

**表記は出典の正式名称をそのまま写す。** `date` と同じ考え方で、台帳の体裁に合わせて空白を足したり削ったりしない。ただし `(移転)` `(再整備)` はこの台帳独自の区別で正式名称の一部ではないので、改名しても残す。

`name` は一意ではない（「道の駅 川崎町」が福岡県と宮城県にある）。改名の結果、**同じ `pref` の中に同じ `name` が 2 つできないこと**は確かめる — レコードの同定が `name` + `pref` なので、重複すると `npm run ci` が落ちる。

### 書く値: pref / city

所在地が実際と違うと気づいたら**修正する**。ただし所在地が特定できず「どちらが正しいか分からない」なら、直さずに `docs/plan-reports.md` に載せる。

`city` は座標のないレコードを市区町村代表点へ落とすための引き当てキーなので、`data/cities.json` の表記に合わせる（`上伊那郡箕輪町` のように郡名を含む形）。`pref` が `data/cities.json` にない値だと `npm run ci` が落ちる。

### 書く値: urls

出典リンクの配列で、要素は `{"title": "...", "url": "..."}`（キー順も固定）。基準は「後から根拠を辿れるか」で、同じことを言っている記事を何本も足す必要はない。足すだけでなく、点検（「既存の出典を点検する」）で 404 や差し替えが分かったリンクは消す・置き換える対象になる。

**リンクだけを置く列で、地の文の置き場所ではない。** 「着工は未定」のような補足は書かない — 状況を表すのは `status` と `date` で、この列が答えるのは「その値の根拠はどこにあるか」だけ。判明したが列に書けないことは `docs/plan-reports.md` に回す。

**`title` は出典ページの見出しをそのまま写す。** 幅の狭い情報ウィンドウに URL が並ぶと何のページか分からないので、地図は `title` をリンクのラベルとして描画する（`src/frontend/components/PlanInfoWindow.tsx`）。**点検で開いたページの見出しは `title` に写し直してよい。** 点検でページを開くのでタイトルは手元にあり、直すのに追加の取得は要らない。義務ではないので、他に書くことがない駅で `urls` を動かすためにやる必要はない。

**`url` は `http` / `https` のみ。** **同じ `url` を 1 レコードに 2 つ置かない。**

### jq で書き換える

**Edit ツールは使わない。** レコードの特定に必要な `old_string` の一意性が取りにくく（`"name": "道の駅 川崎町"` は福岡県と宮城県の 2 件ある）、`urls` の書き換えでは `old_string` が長大になる。jq は既存キーの順序を保持するのでキー順が崩れない。

**jq に in-place がないので、別ファイルに書いてから差し替える。** 同じファイルへリダイレクトすると読む前に空になる。`/tmp` はサンドボックスの書き込み許可に入らないので `$TMPDIR` を使う:

```bash
jq --arg today "$(TZ=Asia/Tokyo date +%F)" '
  (.[] | select(.name == "道の駅 石川町" and .pref == "福島県")) |= (
      .date = "2026-09-18"
    | .checked_on = $today
  )' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

**レコードの特定は `name` と `pref` の両方で行う。** `name` は一意ではないので、`pref` を落とすと別県の同名駅も一緒に書き換わる。`select` は書き換え前の値を見るので、改名するときも旧名で引いて `.name` を代入すればよい。

**値は jq のプログラムに直接埋めず `--arg` で渡す。** プログラム側に埋めると `"` と `\` を jq 用にエスケープすることになり、URL やタイトルでは間違えやすい。`--arg` なら jq 側のエスケープは不要になる。**シェル側は単一引用符で囲む** — そうすれば `$` とバッククォートが展開されない（値に `'` が含まれるなら `'\''` で閉じ直す）。

**一致件数を確かめてから書く。** `select` が 0 件でも jq は成功して元のまま出力するので、書いたつもりで何も変わっていないことに気づけない:

```bash
jq '[.[] | select(.name == "道の駅 石川町" and .pref == "福島県")] | length' data/plans.json
```

**1 駅 1 コマンドで回す。** 複数の駅を 1 つの jq 式にまとめることもできるが、式が長くなるほど取り違えに気づきにくい。駅ごとに書く手順とも噛み合う。

### urls の書き換え

`urls` は配列なので、要素を 1 つずつ触る。**全文を組み直さない** — 差し替えも削除も、`url` の完全一致で対象の要素だけを選べる。

**まず現在値を読む。** 足すだけのときも、同じ出典が既にないかを見る:

```bash
jq -r '.[] | select(.name == "道の駅 川崎町" and .pref == "福岡県") | .urls[] | [.title, .url] | @tsv' data/plans.json
```

**何も出ないなら `select` が引けていない。** `urls` が空のレコードは存在しない（出典のない駅は載せない）ので、空の出力は読み取りの失敗を意味する — 改名済みの駅を旧名で引いた、名前を写し間違えた、`pref` が違う、のどれか。キーを確かめ直すまで書き込まない。

**足す:**

```bash
jq --arg title '道の駅◯◯ 開業日決定' --arg url 'https://example.jp/news/456' '
  (.[] | select(.name == "道の駅 石川町" and .pref == "福島県")) |= (.urls += [{title: $title, url: $url}])
  ' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

**差し替える:**

```bash
jq --arg dead 'https://dead.example.jp/a' \
   --arg title '道の駅◯◯ 開業しました' --arg url 'https://example.jp/news/456' '
  (.[] | select(.name == "道の駅 川崎町" and .pref == "福岡県"))
  |= (.urls |= map(if .url == $dead then {title: $title, url: $url} else . end))
  ' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

**消す:**

```bash
jq --arg dead 'https://dead.example.jp/a' '
  (.[] | select(.name == "道の駅 川崎町" and .pref == "福岡県")) |= (.urls |= map(select(.url != $dead)))
  ' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

**タイトルだけ入れる**（`title` が URL のままのリンクに、点検で見たタイトルを付ける）:

```bash
jq --arg url 'https://example.jp/plan' --arg title '◯◯町 道の駅整備基本計画' '
  (.[] | select(.name == "道の駅 川崎町" and .pref == "福岡県"))
  |= (.urls |= map(if .url == $url then .title = $title else . end))
  ' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

**対象の `url` は読み取り出力からコピーする。** 一致は完全一致なので、1 文字違うと何も起きないまま jq は成功する（`select` の 0 件と同じ壊れ方で、クエリ付きの長い URL でとくに起きやすい）。

**0 件ガードは自分で数える**（「既存の出典を点検する」）。消したあとに残るリンクの本数を書く前に数え、0 本になるなら消すのをやめて元の URL を残す。代替のない死んだリンクが複数あってどれかを残すことになるなら、**後ろの要素（後から足された新しい出典）を残す。**

**書き換えたら `git diff data/plans.json` で確かめる。** 意図した要素だけが動き、同じレコードの他の出典が無傷であることを見る。差分がそのままレビューに出るので、この確認は PR の準備でもある。

### レコードを追加する

台帳にない駅が見つかったら追加する。**`urls` には出典を必ず 1 本以上入れる** — 根拠のないレコードを足さない。

**キー順とレコード順を守る。** どちらも `npm run ci` が検証するので、外すと落ちる（キー順は 9 つを規定の並びで、レコード順は `pref` → `city` → `name`。詳細は CLAUDE.md「開発計画マスタ」）。並べ直しを自分でやらずに済むよう、**末尾に足してから並べ替える**のが早い:

```bash
jq --arg today "$(TZ=Asia/Tokyo date +%F)" '
  . + [{name: "道の駅 ◯◯町", pref: "福井県", city: "◯◯郡◯◯町", status: "計画中",
        date: "2028年度", lat: null, lng: null,
        urls: [{title: "◯◯町に道の駅を整備へ", url: "https://example.jp/news"}],
        checked_on: $today}]
  ' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

並べ替えは `data/cities.json` の出現順が要るので jq 単体では書きにくい。**末尾に足したら位置だけ人手で直し**、`npm test` の「is sorted by prefecture, city, then name」で確認する（落ちると順序が逆転している 2 駅が「A before B」の形で出るので、どこへ動かすかはそこから辿る）。

**座標は分かるなら書く。** 分からなければ `null` にして `city` を `data/cities.json` の表記に合わせる — 地図は市区町村代表点にフォールバックする。両方欠けると地図に出ない。

**重複に注意する。** 既存の仮称（「道の駅 ◯◯町」）と正式名称が同じ駅を指していることがある。追加の前に `jq -r '.[] | select(.pref == "福井県") | .name' data/plans.json` でその県の駅を眺める。

### `checked_on` を押す

**調査した駅すべてに JST の当日を書く。** 新しい情報がなかった駅も対象で、`checked_on` を書き換えるだけの更新が「調べたが変更はなかった」の記録になる。

これは**調査キューの並び替えキー**なので、書き忘れるとその駅は次の周回でまた先頭に引かれ、同じ調査を繰り返すことになる。**CI は `checked_on` を検証しない**（無関係な PR まで落ちてしまうため）ので、押印はこのスキルの責務。

日付は **`TZ=Asia/Tokyo date +%F`** で取る。素の `date +%F` だとマシンのタイムゾーンで決まるので、UTC のマシンでは JST 午前中に前日が入り、キーが 1 日ずれる。

値の変わらない駅は、その駅の書き込みが `checked_on` だけになる:

```bash
jq --arg today "$(TZ=Asia/Tokyo date +%F)" '
  (.[] | select(.name == "道の駅 共和町" and .pref == "北海道")) |= (.checked_on = $today)
  ' data/plans.json > "$TMPDIR/plans.json" && mv "$TMPDIR/plans.json" data/plans.json
```

**押すのは実際に調べた駅だけ。** 10 件に届かないまま終えるなら、調べた分にだけ押して残りは次のセッションに回す。調べていない駅に押すと、調査済みとしてキューの最後尾に回る。

### 列に書けないことは `docs/plan-reports.md` に追記する

値にできなかったものはこのファイルに書く。**末尾に追記するだけで、既存の項目には触らない** — 対応と消し込みは人が行うので、前回までの項目を読んで判断する必要はない。

書くのは:

- **次回の手掛かり** — 中止や凍結を疑ったが宣言が見つからなかった（「書く値: status」）、延期の告知に「時期は改めて公表」と続きが予告されていた（「開業が近いものは『延期』を疑う」）。値は動かせないが、その駅をいつ・何を手掛かりに見直すかの材料になる
- **判断を仰ぎたいこと** — 所在地が資料によって食い違い `city` を確定できない、代替が見つからず 0 件ガードで残したリンク切れ、消したリンクが現在値の唯一の根拠だった

**1 駅 1 項目、文単位で完結させる。** 日付・駅名・都道府県を頭に置く:

```markdown
- **2026-08-11 道の駅◯◯（福井県）** — 市の資料では △△町、県の資料では ×× 町とあり `city` を確定できない。[出典](https://example.com/)
```

**自分で直せることは書かない。** `pref` / `city` の明らかな誤りは直して差分に含める。ここに書くのは**判断を仰ぐもの**と**次回への申し送り**だけ。

## 3. コミットして PR を出す

### lint と test を通す

```bash
npm run lint:fix   # インデントの崩れは Biome が直す
npm test           # src/frontend/plan-data.test.ts が構造を検証する
```

インデントは Biome が正規化するので `jq --indent 4` は必須ではない。`npm test` が落ちたら、`status` の値・`pref` の実在・`name` + `pref` の一意性・レコード順のどれかが崩れている（jq の `|=` で既存キーだけを触っている限り、キー順は崩れない）。

### PR

**1 セッション 1 PR。** 調べた分をまとめて 1 本にする。コミットログは英語で、「何を変更したか」と「その結果何が達成されたか」を書く。

**PR 本文に書くのは 2 つだけ。**

1. **調査した駅の一覧** — 何を調べたか。値が動かなかった駅も含める（差分は `checked_on` の 1 行だけになる）
2. **報告事項** — `docs/plan-reports.md` に追記した内容

**更新したレコードは書かない。** 何をどう変えたかは `data/plans.json` の差分に出ており、その根拠は `urls` のリンクとして差分に入っている。本文で繰り返すと、差分と食い違ったときにどちらが正しいか分からなくなる。

それ以外に伝えたいことがあればコミットメッセージに書く。

### 締めにキューの残りを報告する

最終応答には、差分にもコミットにも出ないものを書く。

1. **キューの残り** — 1 回では一周しないので、次のセッションを走らせるべきかの判断材料になる
2. **持ち越した駅** — 名指しされて 10 件に収まらなかった駅（キューの順番に乗らないので、書かないと次に何を調べるべきか分からなくなる）

キューは押印より後に数える。**押印より前に数えてはいけない** — 今調べた 10 件が古いままの側に数えられる。

```bash
jq '[.[] | select(.status == "登録済み" or .status == "計画中" or .status == "凍結")] | sort_by(.checked_on) as $entries
    | ($entries[0].checked_on) as $oldest
    | {total: ($entries | length),
       oldest: $oldest,
       at_oldest: ([$entries[] | select(.checked_on == $oldest)] | length)}' data/plans.json
```

> 対象は全 ◯◯ 件。いちばん古い `checked_on` は YYYY-MM-DD で ◯◯ 件。

`at_oldest` は最古のスタンプを共有する件数で、ここが 10 件ずつ削られていくことで一周が進む。

`oldest` がまだ古いなら「続きは新しいセッションで」を添える。全件が十分に新しければ足さない — 一周し終わった直後にもう一度走らせても、いちばん新しい駅を調べ直すだけになる。
