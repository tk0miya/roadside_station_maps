# 道の駅整備計画マップ

これから開業する道の駅、整備や登録が進んでいる道の駅を地図に出す。既存の駅を michi-no-eki.jp から取り込むメインの地図とは別物で、データ元は人手と調査セッションが育てる台帳 `data/plans.json` である。

この文書は**台帳が満たすべきこと**（第 1 部）と**それをどう実現しているか**（第 2 部）を扱う。調査と書き込みの手順は `.claude/skills/michi-no-eki-plan-research/SKILL.md` にあり、アルゴリズムは各実装のコメントにある。

## 仕組み

### アーキテクチャ

**このリポジトリが唯一のマスタで、マスタと配信物が同一。** 地図は `data/plans.json` をそのまま読む。生成やビルドの工程を挟まないので、マスタを直せば配信されるデータが直る。中間生成物のコミット漏れという失敗モードが存在しない。

**メインの駅マップから独立している。** 認証もバックエンドも使わず、スクレイピングのパイプラインとも無関係。台帳が壊れてもメインの地図は動き、その逆も同じ。

**読み手は 2 系統ある。** 地図は読むだけ、編集の道具は読んで書く。両者が共有するのは `data/plans.json` の形だけで、コードは共有しない。この形が契約なので、以下の規約は片方の都合ではなく両方への要求になる。

### データ構造

1 要素 1 駅の JSON 配列（現在 177 件）。列は 9 つで、**キー順もこの並びで固定する**。

| 列 | 役割 |
|---|---|
| `name` | 駅名。正式名称が決まるまでは仮称（「道の駅 ◯◯町」の形） |
| `pref` | 都道府県。`city` と合わせてレコードの所在地を決める |
| `city` | 市区町村。座標のないレコードを代表点へ落とす引き当てキー |
| `status` | 計画がどこまで進んだか |
| `date` | 開業（予定）日 |
| `lat` / `lng` | 座標。判明していなければ `null` |
| `urls` | その値をどこで確かめたかの出典リスト |
| `checked_on` | その駅を最後に調査した日 |

座標だけが数値または `null` で、残りは文字列。**値がないときは空文字列にする**（文字列の列に `null` を入れない）。`urls` は配列で、要素のキー順も固定。

#### 列ごとの規約

**`status` は 5 値のみ** — `計画中` / `登録済み` / `開業` / `凍結` / `中止`。

- **登録は必ずニュースになる。** 国交省の登録は年 2 回（6 月・12 月）にまとまって公示され、登録証の交付は自治体の発表や地方紙の記事になる。自治体が「登録を目指す」と書いているだけでは `計画中` のまま
- **`開業` は実際に開いたことが確認できたときだけ。** `開業` と `中止` は調査の対象から外れるので、誤って倒すと人が手で戻すまで調査対象に戻らない
- **`凍結` と `中止` は自治体がそう宣言したときだけ。** どちらに入れるかは**計画が終わったと言っているか**で分ける

| 発表の言葉 | 書く値 | |
|---|---|---|
| 凍結・休止・一時中断 | `凍結` | 止まっているだけで、再開しうる |
| 中止・白紙撤回・断念・見送り・廃止 | `中止` | 終わったと言っている |
| 延期 | どちらでもない | 日程が動いただけなので `date` を書き換える |

**宣言の言葉が出るまで `status` を動かさない。** `登録済み` を `計画中` に落とすのも同じく禁止 — 調査対象には `登録済み` も入るので、疑いを理由に登録の確定情報を巻き戻さない。中止や凍結を**疑わせる**材料はいくらでも出てくる（数年間更新がない、予算が計上されなくなった、公式ページが消えた、推進していた首長が交代した）が、どれも根拠にはならない。疑いの段階で `中止` を書くと、生きている計画を終わった話として台帳から消すことになる。**`凍結` も疑いの逃げ場ではない** — 動いていないように見えることは `凍結` の根拠でもない。

`凍結` は調査対象に残る。再開が発表されたら `計画中` に戻し、中止が宣言されたら `中止` に倒す。

**`date` は判明している粒度をそのまま記録する列。** `2026-09-18` も `2026` も `2026夏` も等しく正しい値で、形式は決めない。**変換してよいのは和暦 → 西暦だけ**で、それ以外は出典の言葉をそのまま写す。

| 出典の表現 | 書く値 | |
|---|---|---|
| 令和 9 年 7 月オープン | `2027-07` | 月まで言い切っているので日付形式にできる |
| 令和 9 年度初頭 | `2027年度初頭` | ✗ `2027-04` — 「初頭」が何月かは出典が言っていない |
| 令和 9 年夏ごろ | `2027夏ごろ` | ✗ `2027-07` |
| 2028 年度 | `2028年度` | ✗ `2028` — 年度は 2029 年 3 月まで含む |
| 2026 年度下半期 | `2026年度下半期` | ✗ `2026` — 暦年をまたぐ |

「初頭」「上半期」「ごろ」を月に置き換えるのは、出典にない情報を足す行為で、**後から見たときに確定情報と区別がつかなくなる**。これがこの列でいちばん避けたい壊れ方なので、粒度を上げる方向にも下げる方向にも丸めない。年度と暦年の区別だけは意識しておく（「令和 9 年度」は 2027 年 4 月〜2028 年 3 月であって 2027 年ではない）が、気づいたからといって暦年に直すのではなく年度のまま書く。

**`pref` / `city` は `data/cities.json` にある表記で書く。** `city` は `上伊那郡箕輪町` のように郡名を含む形、政令市は `さいたま市岩槻区` のように区まで。**載っていない表記は書かない** — 座標のフォールバック先を引き当てるキーで、レコード順もこのテーブルが決めるため。

**`cities.json` は別の経路で更新されるので、この台帳がそれに従う。** 改称・合併・分割に追随していなければ、**その所在地を含む市区町村を `cities.json` から選んで書く**（改称なら旧称、合併なら合併前のどれか）。座標が落ちる先になるので、その場所を含む方を選ぶ。**`cities.json` 自体は台帳側から直さない。**

**`lat` / `lng` は分かるなら書く。** 分からなければ `null` で、`city` の代表点に落ちる。両方欠けると地図に出ない。

**`urls` は出典リンクだけを置く列。** 要素は `{ title, url }`。地の文は書かない — 状況を表すのは `status` と `date` で、この列が答えるのは「その値の根拠はどこにあるか」だけ。判明したが列に書けないことは `docs/plan-reports.md` に回す。

- **リンクを構造として持つ**: この列に入るのは出典リンクだけなので、記法を決めて 1 つの文字列に詰めると、書くたびに記法を守らせ、読むたびに解析することになる。配列なら書き手も読み手も分解しなくてよい
- **`title` は出典ページの見出しをそのまま写し、空にしない。** 地図はこれをリンクのラベルとして描画するので、URL だけが並ぶと何のページか分からず、空だと押せないリンクが並ぶ

出典の格には順位がある。

1. **自治体の公式サイト** — 一次情報。ただし更新が遅く、決定済みの情報が載っていないこともある
2. **地方紙・地方建設業紙** — 開業日の速報はここが早い。優先交渉権者の決定なども載る
3. **国交省・地方整備局** — 登録の確定情報
4. まとめサイト・個人ブログ — 古い情報が残りがちなので、他に裏が取れないときの補助に留める

**同じ順位の出典が同じ内容を報じているなら、全文が読める無料記事を優先する。** 有料記事を置くと後から根拠を辿る人が確かめられず、肝心の開業日が有料部分にあることもある。ただし**この優先は順位をまたがない** — 無料のまとめサイトが有料の地方紙を追い越すことはない。

**下限は 1 件。** 根拠のないレコードを作らない。代替の見つからないリンク切れを消すと 0 件になる場合は、**辿れない URL を残す**（以下「0 件ガード」）。根拠が 1 つもないレコードにするより、Web アーカイブから拾える余地がある方がまし。**残す 1 本を選ぶことになったら、公開日の新しい方 → 出典の格が上の方 → 配列の後ろの要素**の順で決める（配列の位置を最後の手段にするのは、差し替えが要素をその位置で上書きするので、後ろが新しいとは限らないため）。

**このガードは本数しか見ない。** 消す 1 本が現在値の唯一の根拠だったとしても、本数が足りていれば消してよく、**その事実は人に渡す**（→ 相談する）。値ごとの判断をガードに持たせない。

**上限は 10 件。** 上限がないと古い記事が積もり、新しい出典がその中に埋もれる。上限があれば 10 件に達した駅では 1 本足すたびにいちばん弱い 1 本を見直すことになり、出典が新陳代謝する。

上限に達したときの判断は 0 件ガードとは違う。**落とす 1 本を選べる状況なので、根拠として要るかどうかを見る。** 10 件に達したレコードに足すときは、**現在値の唯一の根拠を落とす候補から外す** — その 1 本を消すと `date` / `status` / `name` が何を見て決まったのか辿れなくなる（唯一の根拠は 3 列分しかありえないので、10 本のうち 7 本以上は必ず候補に残る）。残りは足す 1 本も含めて採点し、合計のいちばん低い 1 本を落とす。

| 観点 | 加点 |
|---|---|
| 情報ソース | 出典の格の 1 位 +4 / 2 位 +3 / 3 位 +2 / 4 位 +1 |
| 内容 | 開業日・開業予定が書かれている +3 / 整備や開業が動いた発表（着工、契約、登録、延期） +2 / 開業スケジュールに影響しない進捗報告 +0 |
| 新しさ | 調査日から 1 年以内 +2 / 3 年以内 +1 / それ以前 +0 / 公開日が分からない +0 |

同点で情報ソースの加点も同じなら全文無料の方を残し、それでも決まらなければ公開日の古い方を落とす（公開日が分からないものはいちばん古い扱い）。**内容と新しさでは順位が逆転しうる** — 何年も前の公式ページより、開業日を報じた先月の地方紙の方が今の値の根拠になる。落ちるのが足す 1 本ならそのまま足さない。ただし今回書き換えた値の根拠なら、根拠を外に置いたレコードを作らないために既存の 1 本を落とす。

**`checked_on` はその駅を最後に調査した日。** 調査は古い順に少しずつ進めるため**この列は調査キューの並び替えキー**で、書き忘れるとキューが進まなくなる。

#### ファイル全体の規約

- **キー順を固定する**: 差分の安定のためだけでなく、`name` が一意でない（「道の駅 川崎町」が福岡県と宮城県にある）ため、レコードを特定するには `name` の直後に `pref` が来る必要がある
- **レコード順を固定する**（`pref` → `city` → `name`、`pref` と `city` は `data/cities.json` の出現順 = 全国地方公共団体コード順）: 順序が動くと差分が壊れる。都道府県順にすると GitHub の編集 UI で目的の駅に当たりが付く。表示順は別物で、読み込み後に決まる
- **単一ファイルにする**: マスタがそのまま配信ファイルになりビルド工程が増えない。1 駅 1 ファイルにするとバンドル生成が必要になり、生成物のコミット漏れという失敗モードを新たに作る。この規模ならコンフリクト耐性のためにそれを払う価値はない
- **`name` + `pref` が一意**: レコードの同定に使うので、改名で同じ `pref` の中に同じ `name` を作らない

### 表示への変換

**`status` の 5 値は表示カテゴリ 6 値になる。** `計画中` だけが `date` の有無で `計画中(予定あり)` / `計画中(未定)` に割れ、残りは 1 対 1 で対応する。`date` に日本語混じりの表記が入っても壊れないのは、この振り分けが `date` の**有無**しか見ないため。

**座標がなくても地図に出す。** `lat` / `lng` が `null` なら `city` の代表点にフォールバックし、レコードは「正確な座標」「市区町村の代表点」「解決できなかった」の 3 状態を持つ。3 番目だけが地図に出ない。この区別を残すのは、代表点で描かれた駅を「座標が未調査の駅」として見分けられるようにするため。

**表示順はカテゴリごとに決まる。** `開業` / `登録済み` / `計画中(予定あり)` は開業（予定）日順、`計画中(未定)` / `凍結` / `中止` は都道府県順。どちらも同着は都道府県 → 市区町村 → 名前で決める。

**粒度を丸めないまま順序を作る。** `date` は粒度が混在する列なので、順序付けは値を日付に変換せずに行う。`2026年度` を 4 月と解釈して並べると、台帳が避けている「確定情報との区別がつかない」状態を順序の側で作ってしまう。

**`urls` は出典リストとして情報ウィンドウに描く。** `title` がラベル、`url` がリンク先になる。

## ツールキット

### 書く

台帳の書き換えは `npm run plan` で行う。**Edit ツールは使わない。** 数千行の JSON では `old_string` の一意性を取るのが難しく（`"name": "道の駅 川崎町"` は 2 件ある）、`urls` の書き換えでは長大になる。

**このマスタの壊れ方は「書いたつもりで何も起きていない」。** レコードを引けていないだけなのでファイルは正しいまま残り、検証では捕まらない。CLI はそれを exit 1 にするために置いてあり、失敗したときは `data/plans.json` に触らずに終わる。

サブコマンドと引数は `npm run plan -- --help` にある。CLI の設計（借り出してから書き換える形、レコード順の比較関数を検証側と共有する形）とその理由は `src/lib/plan-master.ts` のコメントにある。

### 守らせる

**規約の検証は `npm run ci` に載っている。** `src/frontend/plan-data.test.ts` がフィクスチャではなく `data/plans.json` の実データを読むので、これが通れば台帳自体が規約を満たしている。

**ただし `checked_on` は載せない。** 押されていないことを CI で落とすと、台帳に触らない無関係な PR まで赤くなる。この列を進める責務は調査スキルにある。

### 調べる

`checked_on` の古い順に少しずつ調べて台帳を最新化する。手順は `.claude/skills/michi-no-eki-plan-research/SKILL.md`。

**1 セッションで 10 件だけ、1 セッションに 1 回だけ。** WebSearch の回数上限がターンではなく Claude Code のセッション単位でかかるため、全件を一度に調べようとすると途中で使い切って、どこまで終わったのか分からない状態で止まる。少しずつ進めて**セッションを分けて繰り返し一周させる**設計にしている。2 バッチ目を始めないのは、上限の残量を知る手段がなく、収まるか判断できないまま始めて枯渇すると、その回の調査が無駄になるため。

これが `checked_on` を列として持つ理由でもある。1 回で一周しない前提なので、どこまで進んだかをデータ側に持たないとキューが成立しない。

### 相談する

調査で出たもののうち**メンテナが判断しないと先に進めないもの**、または**調査でしか気づけず台帳の外を直さないと解決しないもの**を `docs/plan-reports.md` に書く。書式は同ファイルの冒頭にある。

具体的には、資料が食い違って値を確定できない場合、現在値の根拠がデータから消えた場合（0 件ガードで残したリンク切れ、消したリンクが唯一の根拠だった）、`cities.json` が実世界に追随していない場合。

**調べた結果として値を動かさなかったこと自体は書かない。** 中止や凍結を疑ったが宣言が見つからなかった、という否定的な結果も含む。これは値の変わらなかったすべての駅で成立するので、書き始めると報告が調査ログになる。同じ調査は次の周回でもう一度でき、調べた跡は `checked_on` の差分に残る。

**調査セッションは末尾に追記するだけで、対応と消し込みはメンテナが行う。** 読んで判断する責務を調査側に持たせない。

Issue にしないのは、ファイルなら contents 権限だけで扱えて、GitHub API に到達できないセッションでも調査ループが完結するため。PR の差分に出るのでレビューで必ず目に入る。
