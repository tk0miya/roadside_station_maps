# 道の駅整備計画マップ

これから開業する道の駅、整備や登録が進んでいる道の駅を地図に出す。既存の駅を michi-no-eki.jp から取り込むメインの地図とは別物で、データ元は人手と調査セッションが育てる台帳 `data/plans.json` である。

この文書は**整備計画マップの仕様**（「仕組み」）と**台帳を保守する道具と運用ルール**（「ツールキット」）を扱う。調査と書き込みの手順は `.claude/skills/michi-no-eki-plan-research/SKILL.md` にあり、アルゴリズムは各実装のコメントにある。

## 仕組み

### アーキテクチャ

**このリポジトリが唯一のマスタで、マスタと配信物が同一。** 地図は `data/plans.json` をそのまま読む。配信は `data/` をコピーするだけで、生成やビルドの工程を挟まない。

**メインの駅マップから独立している。** 認証もバックエンドも使わず、スクレイピングのパイプラインとも無関係。

**読み手は 2 系統ある。** 地図は読むだけ、編集の道具は読んで書く。両者が共有するのは `data/plans.json` の形だけで、コードは共有しない。

### データ構造

1 要素 1 駅の JSON 配列（現在 177 件）。列は 9 つ。

| 列 | 型 | 内容 |
|---|---|---|
| `name` | string | 駅名。正式名称が決まるまでは仮称（「道の駅 ◯◯町」の形） |
| `pref` | string | 都道府県 |
| `city` | string | 市区町村 |
| `status` | string | 計画がどこまで進んだか |
| `date` | string | 開業（予定）日 |
| `lat` / `lng` | number \| null | 座標 |
| `urls` | array | 出典リンクの一覧 |
| `checked_on` | string | その駅を最後に調査した日（JST） |

文字列の列は、値がないときに空文字列を入れる（`null` にしない）。

#### 各列の定義

**`status`** — 次の 5 値のいずれか。

| 値 | 意味 |
|---|---|
| `計画中` | 整備計画がある。まだ登録されていない |
| `登録済み` | 国土交通省に道の駅として登録された。まだ開業していない |
| `開業` | 営業を開始した |
| `凍結` | 計画が止まっている。再開しうる |
| `中止` | 計画が終了した |

**`date`** — 開業（予定）日。**判明している粒度をそのまま記録する**列で、形式は決めない。`2026-09-18` / `2026-09` / `2026年度下半期` / `2026夏ごろ` / `2026` のいずれもありうる。和暦は西暦に直す。空なら未定。

**`pref` / `city`** — `data/cities.json` にある表記で書く。`city` は `上伊那郡箕輪町` のように郡名を含む形、政令市は `さいたま市岩槻区` のように区まで。`cities.json` は別の経路で更新され、この台帳がそれに従う。

**`lat` / `lng`** — 座標。`null` なら `city` の代表点で描く。

**`urls`** — 出典リンクの一覧。要素は `{ title, url }`（キー順も固定）。1 レコードあたり **1 件以上 10 件以下**。`title` は非空、`url` は `http` / `https` で、同じレコード内で重複しない。

**`checked_on`** — 調査キューの並び替えキーになる。

#### ファイル全体の規約

- キー順は固定（上の表の並び）
- レコード順は `pref` → `city` → `name`。`pref` と `city` は `data/cities.json` の出現順（全国地方公共団体コード順）で並べる
- `name` + `pref` が一意。レコードの同定にこの 2 列を使う
- マスタは単一ファイル

### 地図アプリでの表現

整備計画は**サイドバーの一覧**と**地図上のマーカー**として表現する。

#### 一覧

カテゴリごとにグルーピングする。カテゴリは `status` と `date` の有無から決まる 6 値で、`計画中` だけが 2 つに割れる。

| カテゴリ | 条件 |
|---|---|
| `開業` | `status` = `開業` |
| `登録済み` | `status` = `登録済み` |
| `計画中(予定あり)` | `status` = `計画中` かつ `date` あり |
| `計画中(未定)` | `status` = `計画中` かつ `date` が空 |
| `凍結` | `status` = `凍結` |
| `中止` | `status` = `中止` |

カテゴリは表示の切り替え単位でもある。サイドバーでカテゴリごとに表示・非表示を切り替えると、一覧とマーカーの両方に効く。

グループはこの順に並べ、グループ内の並び順はカテゴリごとに決まる。

| カテゴリ | 並び順 |
|---|---|
| `開業` / `登録済み` / `計画中(予定あり)` | 開業（予定）日順 |
| `計画中(未定)` / `凍結` / `中止` | 都道府県順 |

同着はいずれも 都道府県 → 市区町村 → 名前 で決める。

**日付順は台帳の値を書き換えずに作る。** 比較のときだけ、値を**その表記が意味しうる最後の日**に置き換える（`2026年度` は 2027 年 3 月、`2026` は 2026 年 12 月、`2026冬` は 2027 年 2 月）。同じ日に落ちたときは粒度の狭い表記を先に置く（`2026-12-31` → `2026-12` → `2026`）。

#### マーカー

マーカーの色はカテゴリで決まる。座標は `lat` / `lng` を使い、`null` なら `city` の代表点に落とす。どちらも解決できないレコードは地図に出ない。

マーカーをクリックすると情報ウィンドウが開き、`urls` がリンク集として並ぶ。`title` がラベル、`url` がリンク先になる。

## ツールキット

### 書く

台帳の書き換えは `npm run plan` で行う。

| サブコマンド | 用途 |
|---|---|
| `list` | レコードを一覧する（`--status=` / `--sort=checked_on` / `--limit=` で絞る） |
| `show` | レコード 1 件の現在値を読む |
| `update` | 列の値を書き換える。フラグを渡さなければ `checked_on` だけが進む |
| `url add` / `replace` / `remove` / `title` | 出典を足す / 差し替える / 消す / タイトルを入れる |
| `add` | レコードを追加する |

レコードの同定には `name` と `pref` の両方を渡す。書き込みに成功すると `checked_on` に JST の当日が入る。引数は `npm run plan -- --help` にある。

座標が未記入の駅を埋めるときは、地図上でその地点を右クリックするとクリップボードに `[lat, lng]` がコピーされる。`--lat` / `--lng` に渡して使う。

CLI の設計とその理由は `src/lib/plan-master.ts` のコメントにある。

### 出典を選ぶ

`urls` の下限 1 件・上限 10 件を守るためのルール。出典には格があり、上から順に強い。

1. **自治体の公式サイト** — 一次情報。ただし更新が遅く、決定済みの情報が載っていないこともある
2. **地方紙・地方建設業紙** — 開業日の速報はここが早い。優先交渉権者の決定なども載る
3. **国交省・地方整備局** — 登録の確定情報
4. まとめサイト・個人ブログ — 古い情報が残りがちなので、他に裏が取れないときの補助に留める

同じ格の出典が同じ内容を報じているなら、全文が読める無料記事を優先する。この優先は格をまたがない。

**下限を割るときは消さない。** 代替の見つからないリンク切れを消すと 0 件になる場合は、辿れない URL を残す（「0 件ガード」）。残す 1 本を選ぶことになったら、公開日の新しい方 → 格が上の方 → 配列の後ろの要素 の順で決める。ガードは本数だけを見るので、消した 1 本が現在値の唯一の根拠だったという事実は `docs/plan-reports.md` に渡す。

**上限に達したら入れ替える。** 現在値の唯一の根拠は落とす候補から外し、残りを足す 1 本も含めて採点して、合計のいちばん低い 1 本を落とす。

| 観点 | 加点 |
|---|---|
| 情報ソース | 格の 1 位 +4 / 2 位 +3 / 3 位 +2 / 4 位 +1 |
| 内容 | 開業日・開業予定が書かれている +3 / 整備や開業が動いた発表（着工、契約、登録、延期） +2 / 開業スケジュールに影響しない進捗報告 +0 |
| 新しさ | 調査日から 1 年以内 +2 / 3 年以内 +1 / それ以前 +0 / 公開日が分からない +0 |

同点で情報ソースの加点も同じなら全文無料の方を残し、それでも決まらなければ公開日の古い方を落とす（公開日が分からないものはいちばん古い扱い）。落ちるのが足す 1 本ならそのまま足さない。ただし今回書き換えた値の根拠なら、既存の 1 本を落として入れる。

### 守らせる

規約の検証は `npm run ci` に載っている。`src/frontend/plan-data.test.ts` がフィクスチャではなく `data/plans.json` の実データを読むので、これが通れば台帳自体が規約を満たしている。

### 調べる

`checked_on` の古い順に少しずつ調べて台帳を最新化する。手順は `.claude/skills/michi-no-eki-plan-research/SKILL.md`。

**1 セッションで 10 件だけ、1 セッションに 1 回だけ。** WebSearch の回数上限がターンではなく Claude Code のセッション単位でかかるため、全件を一度に調べようとすると途中で使い切って、どこまで終わったのか分からない状態で止まる。少しずつ進めて**セッションを分けて繰り返し一周させる**設計にしている。`checked_on` を列として持つのはこのためで、どこまで進んだかをデータ側に持たないとキューが成立しない。

### 相談する

調査で出たもののうち**メンテナが判断しないと先に進めないもの**、または**調査でしか気づけず台帳の外を直さないと解決しないもの**を `docs/plan-reports.md` に書く。資料が食い違って値を確定できない場合、現在値の根拠がデータから消えた場合、`cities.json` が実世界に追随していない場合がこれにあたる。書式は同ファイルの冒頭にある。

調査セッションは末尾に追記し、対応と消し込みはメンテナが行う。
