# 計画中道の駅エントリーの更新手順

道の駅 整備計画マップ（`html/plan.html`）のデータ源である Google スプレッドシートの
各エントリーについて、進捗の変化を調査してシートに反映するための手順。

対象範囲は Phase 1 の優先度付けで定める。

---

## 前提と環境要件

### データソース（読み取り）と更新先（書き込み）

human-managed な Google スプレッドシート。読み取りと書き込みで URL が異なる。

| 用途 | 所在 |
|---|---|
| 読み取り（公開 CSV） | `src/frontend/storage/planned-stations-api-client.ts` の `CSV_URL` |
| 更新先（編集ビュー） | `src/frontend/components/PlanSidebar.tsx` の `SHEET_EDIT_URL` |

公開 CSV は「ウェブに公開」された読み取り専用のため、ここには書き戻せない。
Phase 4 の差分は編集ビュー側のシートに反映する。

### スキーマ

```
name,pref,city,status,date,lat,lng,memo
```

| 列 | 内容 | 備考 |
|---|---|---|
| `name` | 駅名 | 空の行はパース時に捨てられる（Phase 0 参照）。仮称の場合あり |
| `pref` | 都道府県 | |
| `city` | 市区町村 | 郡を含む（例 `上伊那郡箕輪町`）。検索時は要正規化 |
| `status` | `開業` / `登録済み` / `計画中` / `中止` | 上記以外は**黙って `計画中` に落ちる** |
| `date` | **開業日**（開業予定日） | 登録目標日ではない |
| `lat` / `lng` | 座標 | 空なら `cities.json` の市区町村代表点にフォールバック |
| `memo` | 備考・根拠URL | 改行区切りで複数URLを保持しうる |

`date` が開業日であることは、既存エントリー（例：福井県あわら市 / 開業 / 2023-04-22 =
「蓮如の里あわら」の開業日）から確認できる。計画中の駅には開業予定日を入れる。

表示カテゴリは `src/frontend/types/plan.ts` の `categoryOf()` が導出する。
`計画中` は `date` の有無で `計画中(予定あり)` / `計画中(未定)` に分岐するため、
`date` を埋めるだけでマーカー色が変わり、地図上で進展が可視化される。

### 必要な egress 許可

ネットワークが制限された環境（Claude Code on the web など）では、以下が許可されていないと
手順が成立しない。**未許可のまま実行しないこと**（理由は「落とし穴」の項を参照）。

| ドメイン | 用途 | 必須 |
|---|---|---|
| `docs.google.com` | CSV 本体の取得 | ✅ 必須 |
| `www.mlit.go.jp` | 登録回の一次情報 | 推奨 |
| `michinoeki.around-japan.jp` | 計画中駅の県別まとめ | 推奨 |
| 各自治体・地方紙のドメイン | 個別記事の精読 | 推奨 |
| `web.archive.org` | 消えた記事の復元 | 任意 |

事前確認：

```sh
curl -sS -o /dev/null -w "%{http_code}\n" "<CSV_URL>"
```

`000` や `CONNECT tunnel failed, response 403` が返る場合は egress 未許可。
egress ポリシーは**コンテナ起動時に適用される**ため、設定変更後は新しいセッションが必要。

## Phase 0：CSV 健全性チェック（外部調査不要）

CSV を取得したら、検索やリンクチェックに進む前に、ローカルで検出できる不整合を潰す。

### 生レコードを見る必要がある検査

`parsePlannedStations()` の返り値では検出できない。パース前の生レコードを見ること。

| 検査 | 問題 |
|---|---|
| `status` 列の生の値が 4 種のいずれでもない行 | `toStatus()` が正規化して `計画中` に変換し、**生の値を捨てる**ため、返り値からは誤分類を追跡できない |
| `name` 列が空でデータのある行 | `parsePlannedStations()` が名前の空な行を落とすため、**マーカーとサイドバーの両方から消え、存在ごと見落とす**。仮称未定の行が該当しやすい |
| `lat`/`lng` に値があるのに `coordSource` が `exact` にならない行 | `toNumber()` が数値化できない値（全角数字・度分秒表記・片方だけ空など）を `null` にし、市区町村代表点へフォールバックする。**実際とは違う位置に黙ってマーカーが出る**。壊れた値は捨てられるため返り値からは追跡できない |

### `parsePlannedStations()` の返り値で検出できる検査

| 検査 | 問題 |
|---|---|
| `coordSource === 'none'` の行 | `pref`/`city` が `cities.json` に無く座標が解決できない。マーカーが出ず地図上では見つからない（`PlanMarkers` が lat/lng で絞るため）。ただしサイドバーの一覧には残る |
| `date` の表記ゆれ | `2027-04` / `令和9年度` などの混在 |
| `name` の重複 | 同一駅の二重登録 |

---

## Phase 1：優先度付け

調査コストは有限なので、陳腐化しやすい順に処理する。

1. `計画中(予定あり)` かつ `date` が実行日より過去 — 最優先。開業済みか遅延のいずれかで、確実に情報が古い
2. `登録済み` — 開業日が確定しやすいフェーズ
3. `計画中(未定)` — 進展があれば `date` が付く
4. `開業` — 再調査不要（正式名称の補完のみ）
5. `中止` — 再調査不要

1 の日付比較について、`date` は `string` のままパースされ正規化されない。
`令和9年度` のような年度表記はその年度末（→ 2028-03）とみなして比較する。
判断に迷う表記は Phase 0 で先に正規化しておくこと。

## Phase 2：駅ごとの照会

### `city` から郡を除去する

この正規化が検出率を決定的に左右する。報道も自治体も郡を付けずに書くため、
CSV の値をそのまま投げると外す。

| クエリ | 結果 |
|---|---|
| `長野県 上伊那郡箕輪町 道の駅 計画 整備` | ヒットなし |
| `箕輪町 道の駅 計画` | 計画の実体を特定 |

### 基本クエリ

```
{郡を除いたcity} 道の駅 計画 after:{実行日の1年前}

例（実行日が 2026-08-08 の場合）:
箕輪町 道の駅 計画 after:2025-08-08
```

`after:` / `before:` は Google の検索演算子で、クエリ文字列に直接書けば効く
（URL パラメータではない）。定期チェック運用では 1 年窓で十分。

### 空振り時のフォールバック

| クエリ | 対象 |
|---|---|
| `{city} 道の駅 登録 目指す` | 既存施設転用型（既存の直売所等を道の駅化する類型。工事イベント語では引っかからない） |
| `{city} 道の駅 整備 基本計画` | 新規造成型 |
| `{city} 道の駅 計画`（`after:` なし） | 全期間再検索 |

全期間再検索の使い方が重要。1 年窓で空振り＋全期間でヒットなら、
「調査済みかつ進展なし」と積極的に確定できる。単なる調査漏れと区別がつく。

### 確認項目

- 現況ステータス（`開業` / `登録済み` / `計画中` / `中止`）
- 期日（開業予定日。登録目標日と混同しない）
- 正式名称（仮称からの確定。開業済みの駅は検索1回でほぼ確実に判明する）
- 直近の進展イベント（登録回・検討委員会・起工式・指定管理者決定・名称決定・予算計上）
- 出典 URL

### 市区町村名の突合（省略不可）

検索結果の市区町村が対象と一致するか必ず確認する。
`after:` で窓を絞るほど、検索エンジンが緩い関連度の結果で埋めてくるため混入が増える。

起こりうる誤マッチ：

- 類似地名の隣接自治体が混入する（例：「○○町」の調査に「南○○村」の施設が出る）
- 窓を絞った際に、無関係な他県の道の駅計画ページが上位に来る

### 記事の公開時期を特定する

本文を開けない場合でも、`after:` / `before:` を動かして在否が反転する境界を挟み込めば
公開時期を特定できる。URL に日付が埋まっていない記事（`article/1197457` 等）に有効。

## Phase 3：リンク健全性チェック

`memo` 内の既存 URL を検査し、辿れないリンクを整理する。

### 判定は三分類（二値にしない）

| 判定 | 条件 | 動作 |
|---|---|---|
| `alive` | 2xx / 3xx | 維持 |
| `dead` | **404 / 410 のみ** | 再検索へ |
| `unknown` | `alive` / `dead` のいずれにも当てはまらないすべて（403, 405, 429, 5xx, タイムアウト, DNS失敗, プロキシ遮断 等） | **削除しない**・保留 |

**`403` を削除条件に含めないこと。** 日本の新聞社サイトは bot 対策やペイウォールで
403 を返すことがあり、記事が生きているのに消される。信濃毎日・中日新聞が該当しうる。

多くのサイトは `HEAD` に `405` を返す。**HEAD → GET のフォールバック**を入れ、
`unknown` のまま滞留させずに `alive` / `dead` へ確定させること。

### 削除より置換を優先

```
dead判定 → 期間指定なしで再検索 → 代替URLが取れたら差し替え
                                 → 取れなければ削除提案（memoの記述自体は残す）
```

記事が消えても、そこに記録された事実は有効なまま。URL だけ削って根拠を失わせるより、
新しい出典に差し替える方が資産が減らない。削除前に **Wayback Machine** の
スナップショットを確認すると、恒久リンクとして復元できる場合がある。

### 自動削除しない

判定結果は Phase 4 の差分レポートに「削除提案」として載せ、人が承認してから反映する。
判定が 1 つ狂うと根拠が消える操作であり、自動実行に向かない。

### memo の複数 URL

`memo` は改行区切りで複数 URL を保持しうる（papaparse が引用符内の改行を処理済み）。
`memo.split('\n')` ＋ URL 正規表現で抽出する。

## Phase 4：差分レポート

全行を並べない。**変更のある行だけ**を出力する。

```
駅名 / 列 / 旧値 → 新値 / 根拠URL
```

例（`計画中(未定)` の駅に開業予定日が付いたケース）：

| 駅名 | 列 | 旧値 | 新値 | 根拠 |
|---|---|---|---|---|
| ○○ | date | （空） | 2027-04 | 地方紙「27年開業目指す」（URL） |
| ○○ | memo | — | 既存施設の道の駅化。2026年度中の登録目標 | 同上 |

反映先は「前提と環境要件」の `SHEET_EDIT_URL`（編集ビュー）。公開 CSV 側には書き戻せない。

## 実行方式：エントリー単位の並列化

エントリー間に依存が無いため、1 エントリー = 1 サブエージェントで並列に調査できる。
Phase 2 と Phase 3 がサブエージェント側、それ以外はオーケストレータ側に残る。

### 分担

| 処理 | 担当 | 理由 |
|---|---|---|
| Phase 0 健全性チェック | オーケストレータ | CSV 全体が対象。1 回で済む |
| Phase 1 優先度付け | オーケストレータ | 全件を見て決める。ここで fan-out 対象を絞る |
| Phase 2 照会 | サブエージェント | エントリーごとに独立 |
| Phase 3 リンクチェック | サブエージェント | そのエントリーの `memo` 内 URL のみ |
| Phase 4 差分レポート | オーケストレータ | 全結果の集約が必要 |
| シートへの反映 | オーケストレータ（人の承認後） | 直列。競合と誤削除を防ぐ |

### サブエージェントへの入力

対象エントリー 1 件（`name` / `pref` / `city` / `status` / `date` / `memo`）と、
Phase 2・Phase 3 の手順一式。他のエントリーの情報は渡さない。

### サブエージェントからの出力

自然文で返させると集約時にパースが必要になり取りこぼす。スキーマを固定する。

```
name        対象エントリー名（照合用）
verdict     変更あり | 変化なし | 要判断
status      調査後のステータス
date        調査後の開業予定日
officialName 仮称から確定した正式名称（あれば）
events      直近の進展イベント
sources     [{ url, publishedWindow }]  publishedWindow は 1年窓の内/外
deadLinks   [{ url, code, replacement }]
note        要判断とした理由など
```

`変化なし` を明示的に返させること。Phase 2 の全期間再検索で確定した「進展なし」と、
単に情報が見つからなかった「要判断」は区別が必要。Phase 4 で両者を書き分ける。

### 並列化で新たに生じる注意点

1. サブエージェントに書き込みをさせない。調査は読み取り専用とし、シート更新は必ず
   オーケストレータ経由にする。N 体が同時に書くと競合し、Phase 3 の「人が承認してから反映」も破れる。
2. 同時実行数を絞る。検索と自治体サイトへの同時アクセスが集中するため、10 前後を上限の目安とする。
3. 市区町村の突合（Phase 2）は各サブエージェント内で完結させる。誤マッチの主因であり、
   オーケストレータは結果しか見ないので、ここを各体に徹底させないと誤情報がそのまま集約される。
4. コストは対象件数に比例する。Phase 1 の優先度付けで fan-out 対象を絞ることが、そのままコスト制御になる。
5. 1 体の失敗で全体を止めない。失敗したエントリーは「未調査」として Phase 4 に報告する。

## 既知の落とし穴

### egress 未許可の環境でリンクチェックを走らせない

制限環境では**生きている URL と存在しない URL が完全に同一の応答になる**。実測：

| URL | 実態 | 応答 |
|---|---|---|
| 長野日報の記事 | 生きている | `000` / CONNECT 403 |
| 信濃毎日の記事 | 生きている | `000` / CONNECT 403 |
| 存在しない 404 用 URL | 死んでいる | `000` / CONNECT 403 |

この状態で Phase 3 を実行すると、**シート内の全 URL が dead 判定され、根拠リンクが全消去される**。
Phase 3 は egress 許可済み環境でのみ実行すること。既定を dry-run にしておくのが安全。

### 登録目標日と開業予定日の混同

同じ駅について「2026年度中の登録を目指す」「2027年4月開業を目指す」の両方が報じられることがある。
`date` に入れるのは開業予定日（この例では `2027-04`）。

### 古い記事が上位に来る

期間指定なしで検索すると、数年前の記事が上位を占めることがある。`after:` の付与で解消する。

## 推奨するスキーマ変更：`checked` 列

現在の CSV には最終確認日の列が無い。そのため：

- 「調べたが変化なし」と「まだ調べていない」が**区別できない**
- 毎回**全行を再調査**することになり、1 年窓を適用する足場が無い

`checked`（最終確認日）を 1 列足すだけで、`checked` が古い行だけを対象にする運用が成立し、
Phase 2 の全期間再検索で確定した「変化なし」も成果として記録できる。

`PlannedStation` 型への追加と `toStation()` でのパースは小さな変更で済む。

## スキル化する際のメモ

この手順を SKILL.md 化する場合の想定：

- frontmatter に `name` / `description` を付与。`description` には
  「計画中の道の駅エントリーの進捗を調査してシートを更新する」旨と、
  発火語（道の駅、計画中、進捗、更新）を含める
- Phase 0 の健全性チェックと Phase 3 のリンクチェッカーは、スクリプトとして
  スキルに同梱すると再現性が上がる。HTTP 部分をインターフェースで切っておけば、
  判定ロジックは既存の Vitest 基盤でモック検証できる
- 「必要な egress 許可」の節は前提条件チェックとして冒頭に置く
