# 道の駅マップ

全国の道の駅を地図に出し、どこへ行ったかを自分で塗っていくアプリ。データ元は michi-no-eki.jp のスクレイピングで、これから開業する駅を扱う整備計画マップ（`docs/plan-map.md`）とは別物である。

この文書は**要件**（何を実現するのか）と**設計**（どうやって実現するのか）を扱う。具体的な手続きやアルゴリズムは各実装のコメントにある。

## 要件

### 地点とルート

**主役は道の駅の地点である。** 地図に出るのも、記録を付ける対象も駅である。

**ルートは地点を結ぶ補助機能である。** そのために、駅のない場所にも地点を置ける — これを**カスタム地点**と呼ぶ。カスタム地点はルートの中にしかなく、訪問の記録は持たない。

### ふたつのモード

地図には**通常モード**と**ルートモード**があり、起動したときは通常モードにいる。

| モード | すること |
|---|---|
| 通常モード | 駅を探し、詳細を見て、訪問を記録する |
| ルートモード | 地点を選んでルートを組む |

**ルートモードへ入るのは 3 通り。** ルートのスイッチを入れると、空のルートで始まる。修飾キー（Cmd / Ctrl）を押しながらマーカーをクリックすると、その駅を 1 つ入れたルートで始まる。修飾キーを押しながら地図をダブルクリックすると、そこにカスタム地点を 1 つ置いたルートで始まる。

**出るのは、スイッチを切るか ESC。** ルートが残るのはルートモードにいる間だけで、出れば組みかけのものは捨てる。

**いまどちらにいるかは常に画面から分かる。**

**分けるのは、同じ操作に 2 つの意味を持たせられないからである。** 訪問を記録するのも、ルートに駅を加えるのも、マーカーに触れることから始まる。どちらのつもりなのかがモードで決まっていれば、触れた結果は迷わず読める。

### 地図で駅を探す

全国の道の駅をマーカーとして地図に置く。マーカーを選ぶと、その駅の営業時間・住所・マップコードと、公式ページへのリンクが出る。起動時、位置情報の取得が許されていれば現在地に地図を寄せる。

駅の一覧は**人手で保守しない**。定期的に出所のサイトから取り直して最新に保つ。

### 訪問を記録する

駅ごとに 5 段階の状態を持ち、マーカーの色で表す。既定は「未設定」で、残る 4 つは色でしか区別しない — **どの色が何を意味するかはアプリが決めず、使う人に委ねる**（訪問済み・車中泊した・行きたい、など）。

状態はマーカーの操作だけで動く。前に進める操作と、未設定に戻す操作の 2 つがあれば足りる。加えて、状態ごとの件数を地図上に常時出す。未設定の件数は「全駅数 − 記録のある駅数」で、駅の総数もここから読める。

### 記録を持ち歩く・見せる

- **ログインすれば、どの端末からも同じ記録が見える。** 記録は駅の状態だけで、それ以外の個人データは持たない
- **ログインしなくても地図は触れる。** 色も塗れるが、その場限りで保存しない（ゲスト）
- **自分の記録を読み取り専用の URL で他人に見せられる。** 見る側はログイン不要で、書き換えはできない。URL からは持ち主が誰なのか分からない

### ルートを組み立てる

地図から複数の地点を順に選び、Google マップのルート案内へ引き渡す。キーボードのない端末でも、順序の入れ替えを除いて組み立てられる。ルートモードでできることは 5 つ。

- **地点を選ぶ。** 選んだ順に並びへ入り、外すこともできる。選べる数には上限がある
- **カスタム地点を置く。** 宿や道の分岐など、駅ではない場所も経由地に混ぜられる。置いた後で位置をずらせる
- **順序を入れ替える。** 選び終えた後で並びを変えられる
- **並びを読む。** どの地点が何番目かは地図上のマーカーが持つ番号が示す。いま何地点で、上限まであと何地点かは常に見える
- **Google マップへ渡す。** 組み上がった並びをルート案内として開く

**経路そのものは扱わない。** 距離や所要時間の計算、ルートの保存はこのアプリの仕事ではなく、Google マップに渡した先の話である。

**順序の入れ替えだけは環境による。** マーカーの右クリックに割り当てるので、右クリックのない端末では届かない。地点は進む順に選ぶので並びが崩れることは少なく、崩れても外して付け直せば済み、渡した先の Google マップにも並べ替えがある。

## 設計

### 全体構成

部品は 3 つ。**地図アプリ**（ブラウザで動く）、**駅データ**（リポジトリに置かれたファイル）、**訪問記録の API**（サーバ）。

**サーバが要るのは訪問記録だけ。** 地図も駅データも利用者によって変わらないので、静的ホスティングから配るだけで済む。人ごとに違うのは「どの駅を何色にしたか」だけで、そこにのみバックエンドを置く。結果として、未ログインでもアプリは全機能のうち保存以外が動く。

**駅データは生成物で、リポジトリに commit する。** 出所のサイトを利用者のブラウザから叩かないので、表示は速く、出所へ行くのも更新の巡回だけで済む — 利用者が何人いても、かける負荷は変わらない。データの変化が commit の履歴として残るという副産物もある。

### 地点とマーカーの呼び分け

**地点（stop）** は地図に置く 1 件で、道の駅の地点とカスタム地点（custom stop）がある。違いは駅データを背負っているかどうかだけで、ルートはこの 2 つを並べて作る。コードでも `stop` はこの地図上の 1 件を指す語として広く使い、選ばれているかどうか・ルートの並びに入っているかどうかは問わない。地点のうちルートに関わる部分だけを指すときは `routeStop(s)` のように `Route` を添えて区別する。ルートの中では、駅の地点だけを指す述語や型を置いていない — 判定はいつもカスタム地点かどうかで足りる。

**マーカー（marker）** は地点を地図上に描いたものを指す。選ぶ・外す・順序を入れ替えるのは、いずれもマーカーのイベントに付く。カスタム地点のドラッグも同じで、動かすのは並びではなく座標である。番号は並びの位置から描く。

**Point** は型の名前としてだけ使い、地点の意味では使わない。地図上の座標を表すのは `LatLng` である。

### 駅データ

出所のサイトを都道府県 → 駅 の階層で辿り、駅 1 件を 1 つの地点として書き出す。持つ項目は 都道府県・駅名・住所・電話・営業時間・マップコード・公式ページ URL・座標。取り込むときに全角と半角、改行や記号の揺れを正規化する。

**駅の同定には出所のサイトが振る駅 ID を使う。** 訪問記録もこの ID を鍵に持つので、駅名が変わっても記録は追随する。逆に、データ更新で消えた駅の記録は宙に浮くため、起動時に照合して落とす。

**差分が読める形で書き出す。** 1 駅 1 行、駅 ID 順に整列する。掲載順はサイトの都合でいつでも変わりうるので、そのまま並べると中身が同じでもファイル全体が書き換わり、更新で何が変わったのかを追えなくなる。

**座標の取れない駅も地図に載せる。** 落とすと件数からも消えて「全駅数」が嘘になる。代わりに全国のどこか 1 点へ置き、次の更新が本当の位置を持ってくるのを待つ。

### 駅データの更新

**週に一度、定期実行で取り直す。結果は直接 commit せず PR として出す。** PR は人が止める関門ではない — 承認も取り込みも自動で流れる。挟む理由は、生成物にも他の変更と同じ検査を通してから入れることにある。人の目が入らない以上、前掲の「差分が読める形」だけが、後から何が変わったのかを追う手段になる。

**巡回は急がない。** 出所のサイトは他人のもので、こちらの都合で負荷をかけてよい相手ではない。取得の間隔を空け、1 回の更新に時間がかかることを受け入れる。

### 訪問記録

記録は **駅 ID → 状態** の対応だけで、未設定の駅は記録を持たない（0 件が既定状態を意味する）。この形は保存先によらず同じである。

**保存先は 3 通りあり、地図側はどれが使われているかを知らない。** 読み書きの窓口を 1 つに揃え、アプリの状態に応じて裏側を選ぶ。

| 状態 | 保存先 | 永続化 |
|---|---|---|
| 共有 URL で開いた | 共有 API から取った記録（読むだけ） | しない |
| ログイン済み | 訪問記録 API | する |
| 未ログイン | メモリ上（ゲスト） | しない |

**画面はすぐ変わり、送信は遅れて届く。** 色は手元の状態を書き換えた時点で変わり、サーバへの反映は少し待ってからまとめて送る。同じ駅を続けて叩いても要求は 1 回に畳まれる。送信に失敗しても操作は止めない — 失われるのは駅 1 件の色であり、地図を使えなくするほどの損失ではない。

### API

リソース指向で、認証が要るものと要らないものを分ける。

| 区分 | 内容 |
|---|---|
| 公開 | ヘルスチェック / ログイン（セッションの発行） / 共有記録の取得 |
| 要認証 | 訪問記録の取得・登録・削除 / 自分の共有 ID の取得 |

保存するのは 2 つだけ — **訪問記録**（利用者・駅・状態・更新時刻）と**共有 ID**（1 利用者 1 個）。

### 認証

**ログインの瞬間だけ Google に頼り、以後は自前のセッションで回す。** Google の ID トークン（有効期間およそ 1 時間）は受け取った 1 回だけ検証し、そこから長期のセッショントークン（1 年）を発行する。以後の呼び出しはこのセッションだけを見る。セッションは残期限が半分を切ったときに黙って延長し、無効なら手元のセッションを捨てて再ログインを促す。

設計判断:

- **Google からは身元だけもらう**: 継続的に Google の API を呼ぶ用途がないので、認可コードの交換や Google 側のリフレッシュトークンは要らない。ID トークンを 1 回検証すれば足りる
- **セッションはサーバに持たない**: 署名の検証だけで通す。半年より短い間隔で開いている限り失効しない。即時に無効化する必要が出たら、そのときセッションの台帳を持つ
- **サイレント再認証には頼らない**: 複数の Google アカウントを使っている環境で機能しないため、長いセッションと自動延長で代替する
- **利用者の識別子は外に出さない**: Google が返す識別子はクレデンシャルではないが、ログ・URL・他人向けの応答には載せない。共有は所有者の識別子を晒さず、別に発行した ID を介する

セッションの署名鍵は運用側の秘密として持つ。**鍵を入れ替えると全利用者が強制ログアウトされる。**

### 共有

**共有 URL に載るのは、所有者の識別子とは無関係に発行した ID だけ。** 1 利用者 1 個で、一度発行したら使い回す。この ID から引けるのは訪問記録の一覧に限られ、書き換える経路はない。

**共有 ID を知っていれば誰でも読める。** 推測できない ID であることだけが防御で、それ以上の権限管理は持たない — 守っている中身は「どの駅に行ったか」であり、この釣り合いで足りる。

### ルート作成

**選んだ地点の並びを Google マップのルート URL に組み立てて開くだけ。** 経路計算を持たないので、地図に必要なのは「順序付きの地点リスト」だけである。

- **駅もカスタム地点も、地図上では同じ 1 本の並びに入れる。** 番号付け・削除・並べ替えが 1 つの経路で済む。代わりに、駅であることを前提にする処理はカスタム地点を避けて通る必要がある
- **駅は名前と所在地の組で、カスタム地点は座標で渡す。** 駅名だけでは駅を一意に指せない。カスタム地点にはそもそも検索できる名前がない
- **地点数の上限は Google マップ側の受け入れ数から決まる。** 上限に達したら、それ以上は選べない
- **ルートモードに入った後は、マーカーに触れた結果をモードだけで決め、修飾キーは見ない。** 修飾キーで切り替えると、キーのない端末に別の操作体系がもう 1 つ要るうえ、キーを離した瞬間に同じ指の動きが別の意味に変わり、組みかけのルートを巻き込む。モードなら操作体系は 1 つで済む
- **修飾キー + マーカーのクリックは入口にしか使わない。** スイッチを入れてから同じマーカーをタップするのと着く先が同じで、1 手短いだけである
- **修飾キー + 地図のダブルクリックは、モードの内でも外でも「押した場所にカスタム地点を 1 つ置く」。** 外ではその地点を最初の 1 つとしてモードが開く。モードで意味が変わらないので、キーを離した瞬間に別の意味に変わるという上の問題を持たない — 離したときに失うのは置きかけの 1 地点だけで、組みかけのルートには届かない
- **修飾キーを押している間は、地図のダブルクリックによるズームを止める。** 同じ指の動きで地点を置くので、拡大と両方が起こってはならない。止めるかどうかはモードで変えない — モードを見て切り替えると、モードが開くその瞬間にズームが戻り、開いたきっかけのダブルクリックがそのまま拡大として読まれる
- **モードの入り切りはトグルスイッチで示す。** 入る操作と出る操作を別のボタンに割り振ると、いまモードの中にいるのかを操作の名前から読み取ることになる。入 / 切のある 1 つのスイッチなら、状態そのものが画面に出ていて、切り替える先も同じ場所にある — スマートフォンで設定の入り切りに使われている形をそのまま借りる
- **組み立て中のルートは、地図に触れただけでは畳まない。** 数回の操作で積み上げた並びを、地図の空きに当たった 1 回で失わせない。畳むのはルートモードを終える操作に限る。ルートがモードと同じ寿命を持つのは、通常モードにルートが残っていると、どの操作がそれを壊すのかがまた分からなくなるためである
- **カスタム地点は、地図の中央に出す照準とボタンでも置ける。** 修飾キーのない端末での置き方がこれで、地図を動かして狙いを合わせるので、**指が置きたい場所を隠さない。** ボタンはモードの箱の中に置く — ルートモード中しか使えない操作なので、モードの入り切りと同じ場所にある
- **ルートの中身は地図上のマーカーだけが持つ。** どの駅がどの順で入っているかは、位置と番号で読む。画面に常時出すのはマーカーが示せないもの — 選んだ数と上限、カスタム地点を置く操作、ルートを渡す操作、モードの入り切り — に限り、残りは地図に使う。画面の狭い端末では、地図に残した面積がそのまま扱いやすさになる
- **ルートを Google マップへ渡しても、ルートモードは続く。** 渡した先で気が変わることがあり、組み直しは同じ並びから始められた方が短い

### 配信とデプロイ

- 地図アプリと駅データは静的ホスティングへ、API は別のサービス（サーバレス + その付属データベース）へ、それぞれ独立して出す
- 静的側で配信のたびに行うのは**アプリのバンドル**だけ。駅データもマスタもリポジトリにある物をそのまま配り、配信の経路にスクレイピングや再生成を挟まない
- API 側には 2 つの設定が要る — 公開してよい Google のクライアント ID と、セッションの署名鍵。前者は設定ファイルに平文で置き、後者はプラットフォームのシークレットとして投入する
- 駅マップと整備計画マップは別ページとして同じ配信物に同居する。共有するのは配信の仕組みだけで、データも認証も別
